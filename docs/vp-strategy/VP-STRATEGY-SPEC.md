## 1. 策略一句话与边界声明

**策略**：用三种时间跨度的成交量分布（Volume Profile）定位真实的筹码交换密集区，在价格回踩密集区且抛压衰竭时买入，在结构阻力或主力派发迹象出现时卖出。

**这套策略与 rQuant 现有边界的关系（经代码核实后修正）**：

| 策略需求 | rQuant 现状 | 冲突程度 |
|---|---|---|
| 跨日 VP / POC / 价值区 | **已实现**：`src/rquant/volume_profile.py`（551 行），含 POC、价值区、支撑阻力候选、风控计划，已接入筛选与 paper 风控 | **不冲突**，既成事实 |
| 分钟级 VP 计算 | 已实现（基于 `minute_bar` 表，云端 4750 万行） | 不冲突 |
| 封单量 / 开板次数（**日频**） | **已落库**：`limit_list_daily.fd_amount`/`open_times`、`limit_up_pool_daily.seal_amount`/`break_count`、`kpl_list_daily.limit_order` | 不冲突 |
| 封单量（**盘中实时**） | 无。现有实时源 `rt_min` 不含任何盘口字段 | **需要新数据源**（见 §8.3，代价比预想低得多） |
| 持仓状态机 + 条件单 | 有 `paper.py`（仓位对象 + 退出判定），无条件单、无状态机 | **真正的新增量** |
| 逐笔成交 | 无，且对零售不可得（见 §8.3） | **本规格不依赖，可删** |

> **修正说明**：本文档初稿判断「这套策略三样全占 rQuant 的禁区，应当另起炉灶」。核实代码后这个判断**不成立**——rQuant 早就在算 VP 了，`CLAUDE.md` 边界里的「不做 Level2 / Tick」指的是逐笔与十档，而本策略实际只需要**买一档的挂单量**，那是 Level-1 就有的东西。项目归属结论随之修正，见 §9.1。

**交付形态必须先定死（决定整个系统的严格程度）**：

- **形态 A · 信号提醒**：系统只推送「买入信号 / 卖出信号」，人工执行。→ 执行价与信号价必然偏差，回测必须建模「信号后 N 分钟的成交价」而不是「信号价」。

- **默认取 A**。本文档所有「买入 10%」「卖出 50%」在形态 A 下一律读作「推送一条含仓位建议的信号」。

## 2. 数据字典（Data Dictionary）

> 这是整份规格的地基。**任何字段进入策略前必须先在此登记**。
> 「可用时间」是最容易出事的一列——它决定了信号最早能在什么时刻计算完成，是未来函数的唯一防线。

### 2.1 登记表模板

每个字段必须填满以下 8 列，缺一列不得使用：

| 列 | 含义 | 为什么必须 |
|---|---|---|
| `field` | 字段名 | — |
| `meaning` | 业务含义 | — |
| `unit` | 单位 | rQuant 已踩过坑：`daily_bar.amount` 是**千元**，`rt_min.amount` 是**元**，差 1000 倍 |
| `freq` | 频率 | 日 / 1min / 3s / tick |
| `available_at` | **实际可用时间** | 不是"数据描述的时刻"，是"这条数据最早能被程序读到的时刻" |
| `adjust` | 复权口径 | 不复权 / 前复权 / 后复权 / 不适用 |
| `revised` | 是否有后期修订 | 财务数据会修订，行情数据一般不会，但**停牌/除权会改写历史** |
| `missing` | 缺失语义 | NaN 代表停牌？代表未上市？代表接口失败？三者处理完全不同 |

### 2.2 本策略实际用到的字段（初版，P0 必须补全并实测校验）

| field | meaning | unit | freq | available_at | adjust | revised | missing |
|---|---|---|---|---|---|---|---|
| `close` | 日收盘价 | 元 | 日 | T日 15:00 起，数据商落地约 15:30–17:00 ⚠️实测 | 需明确 | 除权日改写前复权序列 | 停牌=无行 |
| `amount` | 日成交额 | ⚠️**核对单位** | 日 | 同上 | 不适用 | 否 | 停牌=无行 |
| `min_close` | 分钟收盘价 | 元 | 1min | 当根分钟**结束后**约 3–60s ⚠️实测 | 不复权（原始） | 否 | 无成交分钟可能缺行 |
| `min_vol` | 分钟成交量 | ⚠️股 or 手 | 1min | 同上 | 不适用 | 否 | 缺行=无成交，按 0 处理 |
| `min_amount` | 分钟成交额 | ⚠️元 or 千元 | 1min | 同上 | 不适用 | 否 | 同上 |
| `bid1_price` | 买一价 | 元 | 3s | 快照时刻 + 网络延迟 | 不适用 | 否 | 跌停时可能为 0/空 |
| `bid1_vol` | 买一挂单量 | ⚠️股 or 手 | 3s | 同上 | 不适用 | 否 | 同上 |
| `limit_up` | 涨停价 | 元 | 日 | T-1 收盘后可算 | 不适用 | 否 | 新股前5日无涨跌停 |
| `pre_close` | 昨收价 | 元 | 日 | T-1 收盘后 | **必须用不复权**（涨停价基于不复权昨收） | 除权日会变 | — |
| `POC_yest` | 昨日单日 VP 的 POC | 元 | 日 | **T-1 分钟数据全部落地之后** | 见 §3.3 | 否 | 停牌日无值 |
| `C_POC / C_VAH / C_VAL` | 60日复合 VP 三线 | 元 | 日 | T-1 全部落地后 | 见 §3.3 | 否 | 上市不足60日无值 |
| `AVP_POC` | 锚点 VP 的 POC | 元 | 日 | 锚点日至 T-1 落地后 | 见 §3.3 | 否 | 无锚点=无值 |
| `POC_today_real` | 今日实时 POC | 元 | 1min | 当根分钟结束后 | 不复权 | **当日持续变化** | 开盘首根前无值 |

> **⚠️ 三个必须在 P0 用真实数据实测确认、不得凭文档假设的项**：
> 1. 各接口 `amount` / `vol` 的真实单位（写一个断言脚本：分钟 amount 求和 ≈ 日 amount，误差 <1%）。
> 2. 分钟数据的真实落地延迟（盘中每分钟记录「请求时刻 vs 最新可得分钟」的差）。
> 3. T-1 分钟数据在 T 日 9:15 前是否 100% 可得（如果不是，盘前选股就是裸奔）。

### 2.3 复权口径的死规定

**VP 计算一律使用「不复权原始价格 + 除权日重置锚点」，禁止使用前复权。**

理由：前复权序列会随着每次除权**改写历史价格**。今天算出的 60 日 POC = 12.50 元，除权后重算同一段历史，POC 变成 12.05 元。这会导致：
- 回测结果不可复现（同一份代码不同日期跑出不同结果）；
- 回测用了"未来才知道的除权因子"→ **典型未来函数**。

**除权处理规则**：个股在窗口内发生除权除息 → 该个股的所有跨日 VP（复合 VP、锚点 VP）**从除权日重新起算**，除权日之前的成交量分布作废。除权日当天不产生任何买入信号。

## 3. 策略规格（有限状态机）

### 3.0 状态定义

```
S0  OBSERVE     未持仓，在候选池中被观察
S1  ENTERING    今日已触发首笔买入信号，等待尾盘加仓判定
S2  HOLDING     持仓中（T+1 起可卖）
S3  EXITING     触发了卖出条件，正在执行/等待成交
S4  COOLDOWN    今日已清仓或已被淘汰，当日不再产生该票信号
```

**状态持久化要求（硬性）**：每只票的 `(code, trade_date, state, filled_pct, stop_price, sold_pct, broke_board_count, subscribe_level)` 必须**实时落库**，不得只存内存。进程崩溃重启后必须能从库中恢复，且能区分「今天已经卖过 50%」与「还没卖过」。

> rQuant 已经踩过这个坑：surge-watch 的当日累计量在进程重启后归零，导致 2026-07-07 全天早盘信号丢失。同样的错误不能犯第二次。

### 3.1 标的宇宙与分级（Universe）

| 级别 | 名称 | 规模 | 说明 |
|---|---|---|---|
| L0 | 全市场 | ~5400 | 所有 A 股 |
| L1 | 候选池 Watch | ⚠️目标 50–300 | 通过盘前静态筛选 |
| L2 | 触发池 Focus | ⚠️目标 5–30 | 价格已接近买点，需要高频监控 |
| L3 | 持仓池 Position | 0–4 | 已建仓，需要盘口级监控 |

**L0 硬性排除（C1）**：
- ST / *ST / 退市整理期
- 上市不足 90 个自然日
- 当日停牌 / 盘中临时停牌
- 昨日一字涨停或一字跌停（无法形成有效 VP）
- ⚠️待定：是否排除北交所（涨跌幅 ±30%，流动性差异大）
- ⚠️待定：日均成交额下限（建议 ≥ 5000 万，保证容量，见 §5.4）

### 3.2 数据订阅生命周期 ⭐（原策略缺失，本轮补全）

> **为什么这是必须补的**：原策略假设「随时能看到任意股票的实时 POC、5分钟量能、封单量」。这个假设在工程上不成立——不同数据的获取成本差三个数量级。不做订阅分级，要么打爆 API 配额，要么存储爆炸（见 §8.1 的数据量测算）。
>
> **订阅分级不是优化项，是可行性前提。**

#### 3.2.1 订阅矩阵

| 级别 | 订阅的数据 | 频率 | 单票日数据量（量级） | 全池日数据量 |
|---|---|---|---|---|
| L0 | 日线 OHLCV | 1次/日 | ~100 B | ~0.5 MB |
| L1 | 1分钟 K 线 | 240次/日 | ~10 KB | 0.5–3 MB |
| L2 | 五档盘口快照 | 3s（4800次/日） | ~1 MB | 5–30 MB |
| L3 | 五档盘口 + 委托队列 | 3s | ~2 MB | ≤8 MB |

#### 3.2.2 升级 / 降级规则（全部带滞回与冷却，防抖动）

**L0 → L1（盘前 09:15 一次性计算，盘中不新增）**

同时满足：
1. 通过 C1 硬性排除
2. `close(T-1) ≥ C_VAH(T-1)`（站在 60 日复合 VP 价值区上界之上）
3. `close(T-1) ≤ AVP_POC × 1.15`（未偏离锚点成本过远）
4. 存在有效锚点：近 15 个交易日内存在「涨幅 >7% 且成交量 ≥ 2× 20日均量」的大阳线

> ⚠️ 若 L1 规模超过上限（建议 300），按 §3.2.4 的打分排序截断，并 **记录被截断的数量**（不得静默截断）。

**L1 → L2（盘中每分钟判定一次，不需要 3 秒级）**

- **升级**：`|P_now − POC_yest| / POC_yest ≤ 1.5%`（比买点缓冲带 0.8% 更宽，留出提前量）
- **降级**：连续 30 分钟脱离 ±1.5% 带 → 降回 L1
- **滞回**：升级用 1.5%，降级用 2.5%（宽于升级），避免在边界反复横跳
- **冷却**：同一只票当日降级后，**15 分钟内不得再升级**
- **上限**：L2 同时最多 ⚠️30 只；超限时按接近度排序，挤掉最远的；被挤掉的记入日志

**L1 → L0（当日淘汰，进 S4 COOLDOWN）**
- `P_now < C_POC`（跌破复合 VP 中枢）→ 当日不再回到 L1
- 盘中临时停牌
- 涨停封板（无法买入，见 C4）

**L2 → L3**：买入信号成交/推送后即升级。

**L3 → 退订**：清仓后 T+1 日收盘退订（保留一天用于复盘卖出质量）。

#### 3.2.3 订阅管理的工程硬要求

1. **幂等**：`subscribe(code, level)` 重复调用无副作用。
2. **持久化**：订阅表落库，不只在内存。重启后按库重建订阅。
3. **TTL 兜底**：每条订阅带过期时间，最长到当日 15:00。防止「只增不减」的订阅泄漏。
4. **退订 ≠ 删数据**：退订只停止新数据流入，已落库的历史一律保留。
5. **配额预算**：启动时按 `L1_max × 频率 + L2_max × 频率` 算出当日最大请求数，与数据源配额比对；超出则**拒绝启动并报警**，不得盘中才发现打爆。
6. **降级路径**：主数据源失败时的 fallback 顺序必须显式定义，且**每次降级必须记日志并在信号上打标**（用降级数据产生的信号可信度不同）。

### 3.3 VP 计算规格 ⭐（原策略缺失，本轮补全）

> **为什么这是必须补的**：原策略反复使用 POC / VAH / VAL / LVN，但从未定义它们怎么算。不定义 = 不可复现 = 回测和实盘必然分叉。

#### 3.3.1 价格分桶（Bin）

```
bin_width = max(0.01, round(ref_price × 0.002, 2))
ref_price = 该 VP 窗口内的均价（或首日收盘价，需固定一种）
```

**理由**：固定 0.01 元 bin 对 3 元股和 300 元股完全不可比——300 元股会被切成 30000 个桶，POC 变成噪声。用相对宽度（0.2%）保证不同价位的股票 VP 形态可比。

⚠️ 待定：0.002 这个系数需要在 P1 用真实数据调（用「POC 位置的稳定性」作为评价指标，而不是收益）。

#### 3.3.2 分钟线 → VP 的成交量分配算法

由于只有分钟 OHLCV（没有逐笔），必须用近似算法。**必须二选一并固定，不得两种混用**：

- **算法 U（均摊法）**：该分钟的成交量在 `[low, high]` 区间内的所有 bin 上**均匀分配**。
- **算法 W（三角权重法）**：以 `(open+high+low+close)/4` 为峰，向两端线性衰减分配。

**默认取 U**，理由：无参数、可复现、行业通用降级方案。W 引入了未经验证的形态假设。

⚠️ P1 必须做一次对照：用有逐笔数据的少量样本（如 20 只票 × 20 天）比较 U/W 拟合 VP 与真实 tick VP 的 POC 偏差，用结果决定是否切换。**在做完这个对照之前，不允许因为「W 回测收益更高」而切换到 W**——那是过拟合。

#### 3.3.2b 分钟拟合的适用边界（v0.3 明确）：回测层用近似，实时层用 tick

分钟拟合**不是本策略的目标形态，是历史数据可得性逼出来的回测层妥协**。两层分开：

| 层 | 数据 | 理由 |
|---|---|---|
| **回测层**（跨日 Composite/Anchored VP + 历史 Session VP） | 分钟 OHLCV + U/W 近似 | A 股历史 tick 对零售不可得或极贵；分钟线能回溯多年。**没有别的选择。** |
| **实时层**（盘中 Session VP、封单、S1–S13 全部执行子策略） | **tick / 盘口快照直构**（iTick 评估中，见 §8.3） | 分钟线在这里既不够快（S2 炸板 10s 确认在 3s 快照下都勉强）也不够准（VP 微观结构、买卖方向全靠猜）。分钟近似仅作 tick 断流后的**降级路径**（S12） |

由此产生一条新的硬要求：**回测层与实时层的 VP 必然存在系统性偏差，这个偏差必须被量化而不是被无视。** 具体做法：
1. P1 对照实验（上文）给出「近似 VP vs 真实 tick VP」的 POC/VAH/VAL 偏差分布；
2. 实盘上线后，P5 影子模式每天回填「当日 tick 构建的 VP vs 分钟近似 VP」的偏差,持续监控是否与 P1 结论一致；
3. 回测报告必须标注「基于分钟近似,POC 定位误差约 ±X 个 bin(P1 实测)」,作为回测结论的置信度折扣。

#### 3.3.3 POC / VA / LVN 定义

- **POC**：成交量最大的那个 bin 的中值价。并列时取**离当前价最近**的那个（需固定，否则不可复现）。
- **VA（价值区）**：从 POC 出发，每次向上或向下**扩展一个 bin**，每次选择「上侧下一个 bin 与下侧下一个 bin 中成交量更大的那侧」，累计到总成交量的 70% 停止。上界 = VAH，下界 = VAL。
  - 边界情形：若某侧已到窗口边缘，则只能向另一侧扩展。
  - 这是标准 Market Profile 的 70% 双向扩展算法，**必须写成单元测试固化**。
- **HVN（高成交节点）**：局部极大值 bin，且其成交量 ≥ 窗口内最大 bin 的 ⚠️60%。
- **LVN（低成交凹陷区）**：满足全部三条的连续 bin 段：
  1. 段内每个 bin 的成交量 ≤ 相邻两侧最近 HVN 成交量的 ⚠️30%
  2. 段宽 ≥ ⚠️3 个 bin
  3. 段两侧各存在一个 HVN（即真的是"夹在两座山之间的谷"）

> **`_value_area` 的算法缺陷（G20，新增缺口）**：现有实现是「把所有 bin 按成交量从大到小排序，累加到 70% 停止，然后取被选中 bin 的最小价和最大价作为 VAL/VAH」。
>
> 问题在于被选中的 bin **不要求连续**。如果价格分布是双峰的（很常见——箱体上沿和下沿各一个峰），top-N 会同时选中两个峰，然后 min/max 把中间那段低成交的区域也一并圈进「价值区」，导致 VA 被系统性拉宽。
>
> 标准 Market Profile 算法是从 POC 出发逐 bin 向两侧扩展（§3.3.3），保证价值区是**连续区间**。两种算法在单峰分布下结果接近，在双峰分布下差异显著——而本策略恰恰关心的就是箱体震荡（双峰）形态。
>
> **这个缺陷影响的不只是新策略，也影响 rQuant 现有的 `volume_profile` 风控计划。** 修复时必须重跑依赖它的历史实验。

#### 3.3.5 三种 VP 的窗口定义

| VP | 窗口 | 更新方式 |
|---|---|---|

#### 时段 A：09:30–10:30（开盘冲高期）

### 3.6 封单量监控与条件单 ⭐（原策略缺失，本轮补全）

> 这是你指出的核心缺口。原策略 A2 只写了「触及涨停但炸板放量 → 卖 50%」，但「炸板」和「放量」都没有可执行定义，而且**漏掉了整个封板质量监控体系**——A 股短线里，封板质量比涨停本身重要得多。

#### 3.6.1 封单相关指标定义

| 指标 | 定义 | 数据依赖 |
|---|---|---|
| `seal_vol` 封单量 | 当 `bid1_price == limit_up` 时的 `bid1_vol` | 五档盘口 |
| `seal_amt` 封单额 | `seal_vol × limit_up` | 同上 |
| `seal_ratio` 封成比 | `seal_amt / 当日累计成交额` | 盘口 + 分钟线 |
| `seal_mcap` 封流比 | `seal_amt / 流通市值` | 盘口 + 基础信息 |
| `seal_peak` 当日封单峰值 | 当日 `seal_amt` 的历史最大值 | 需状态持久化 |
| `seal_decay` 封单衰减率 | `1 − seal_amt / seal_peak` | 同上 |

**数据可得性（已调研，结论比预想好得多）**：

1. **封单量只需要买一档，不需要五档。** `seal_vol` 的定义是「买一价等于涨停价时的买一挂单量」——买一价量属于 **Level-1** 范畴，不是 Level-2。这一点在初稿里判断错了。
2. **tushare `rt_k`（doc_id 372，¥200/月）提供 `bid_price1` / `bid_volume1` / `ask_price1` / `ask_volume1` + `num`（开盘以来成交笔数），单次 6000 条即可覆盖全市场**，且是 token 认证、**不吃 IP 反爬**。这是目前唯一一条云端可用、零封禁风险、能拿到封单量的路径。
   - ⚠️ 需在 P0 实测确认两件事：这些字段 `默认显示=N`，必须在 `fields` 里显式请求；以及**实际刷新频率**（官方文档未写，可能不是 3 秒级）。
   - `rt_k` 在 rQuant 现有代码里**完全没有接入**，需要新增 adapter 方法。
3. **封单的日频历史已经在库里**，可以立刻做离线验证，不必等实时接入：

| 字段 | 表 | 来源 |
|---|---|---|
| `fd_amount` 封单金额 / `open_times` 开板次数 | `limit_list_daily` | tushare `limit_list_d` |
| `seal_amount` 封板资金 / `break_count` 炸板次数 / `first_seal_time` | `limit_up_pool_daily` | akshare 东财涨停池 |
| `limit_order` 封单量 / `lu_limit_order` 最大封单 | `kpl_list_daily` | tushare `kpl_list` |

> **这三张表改变了实施顺序**：「封单强度是否真的预测次日收益」这个问题，用日频历史就能回答，**不需要先花钱接实时盘口**。因此本规格把封单因子的**离线验证提前到 P2**，实时监控留在 P4。见 §9.2。
>
> 仍然成立的红线：**绝不用分钟线去「猜」实时封单量**。日频历史用于验证因子有没有用，实时数据用于盘中执行，两者不可互相替代。

#### 3.6.2 「封板 / 炸板 / 回封」的确定性定义

```
封板  SEALED   := bid1_price == limit_up  AND  seal_vol > 0
炸板  BROKEN   := 曾 SEALED，之后 last_price < limit_up 且持续 ≥ 10 秒
回封  RESEALED := BROKEN 之后重新 SEALED，且 seal_amt ≥ 炸板前 seal_amt 的 50%
```

**10 秒的作用**：防止一笔大单瞬间砸穿后立刻回封被误判为炸板。⚠️ 该阈值待 P4 用真实盘口数据标定。

`broke_board_count`（当日炸板次数）必须持久化。**炸板 2 次及以上 → 该票当日强制降级为 S4，不再产生任何买入信号**（原策略完全没有炸板次数的概念）。

#### 3.6.3 封单衰减条件单（状态机）—— v0.3 修正版

> **先纠正 v0.2 的一个机制性错误：封板状态下不存在「卖单排队」。**
> 涨停封板意味着买一价 = 涨停价上压着巨量买单，而卖侧无人挂单——此时以涨停价挂出的卖单会**立即与封单成交**，根本不会进入任何队列。v0.2 写的「先挂涨停价排队锁位置，等崩了再挂排不上队」是错的。
> 排队机制只真实存在于两个场景：想在封板时**买入**（买单排在封单队尾），以及**跌停时卖出**（卖单排在跌停卖队列，见 §3.6.4）。

持仓股封板期间运行，每 3 秒评估一次：

```
        [SEALED · 封板持有]
                │
    seal_decay > 40%  或  seal_amt < 2000万
                ▼
        [WARN · 部分止盈]
    动作：立即以涨停价卖出 50%
    （与封单即时成交，零滑点；
      带 3 秒未成交撤单转对手价的保护，见 S5）
                │
    ┌───────────┴────────────────┐
seal_decay > 70%           剩余仓位继续持有，
或 炸板确认（§3.6.2）       seal_decay 回落 < 25% → 回到 SEALED
    ▼
[FLUSH · 出清]
    动作：剩余仓位以对手价卖出；
    若已炸板，启用追价保护（S5）
    │
last_price < limit_up × 0.97
    ▼
[DUMP · 无条件市价清仓 + 当日拉黑]
```

**为什么封单还在时就要卖——不是为了排队，是为了成交价。** 封单存在的每一秒，你都能以涨停价（当日最高价）即时成交；封单崩溃、价格跌离涨停之后，面对的是正在下坠的对手价，每犹豫一档就低一档。这个状态机权衡的是「继续持有博次日溢价的期望收益」与「炸板瞬间的滑点损失」，40% / 70% 两条线就是这个权衡的量化表达。

**时序风险**：从「检测到衰减」到「卖单到达交易所」有秒级延迟。若封单恰在这个窗口内被撤光，涨停价卖单会变成挂在盘面上方的死单——所以 WARN 的卖出动作必须自带「N 秒未成交即撤单转对手价」保护（条件单 S5），N 建议 3 秒。

⚠️ 全部阈值（40% / 70% / 2000万 / 25% / 3% / 3秒）待 P4 标定。**在拿到真实盘口数据做过分布统计之前，这些数字是占位符，不是结论。**

#### 3.6.4 跌停板的对称处理

持仓股封跌停时：
- 09:15 集合竞价即以跌停价挂卖单（排队位置就是一切）
- 每 3 秒监控卖一封单量 `ask1_vol`
- `ask1_vol` 较峰值衰减 > 50% → 说明有资金接盘，**撤单改为市价卖**（跌停打开瞬间往往是当日最好卖点）
- 若一直未成交 → 次日 09:15 继续挂

| S6 | A5 | **闪崩防误触发** | 跌破 POC 需持续 ≥10s 才触发 A5（对称于 S2） | 防单笔大单瞬间砸穿即收回的误杀 | tick 级 |

| S8 | 执行层 | **委托生命周期状态机** | placed → partial → filled / timeout / cancelled | 部分成交怎么补、超时怎么追价、废单怎么报警——形态 B 的必修课，形态 A 降级为推送里附「建议委托方式」 | 券商回报（形态 B） |
| S9 | C2 | **大单派发监控** | 主动卖单中单笔 ≥⚠️50 万的占比 > 阈值 | 把 C2 的 14:45 清仓提前触发 | 逐笔成交 + 买卖方向 |
| S10 | §3.7 竞价 | **竞价虚挂检测** | 9:20 前的大买单在 9:20（不可撤时点）前撤掉 | 该票当日信号降权/剔除 | 9:15–9:25 竞价盘口序列 |
| S11 | 跌停持仓 | **跌停排队与打开监控** | §3.6.4 | 排队 / 撤单转市价 | 盘口 ask1 |
| S12 | 系统 | **数据断流降级** | 盘口 feed 静默 > ⚠️30s | 自动关闭所有依赖盘口的规则（S1–S11），推送降级通知，止损退回分钟级口径 | — |
| S13 | §3.8.3 停牌 | **复牌重估条件单** | 持仓股复牌事件 | 复牌集合竞价按预设价带挂单；复牌后 5 分钟重评全部条件 | 停复牌事件流 |

**三条结论**：

1. **S2 / S6 / S7 / S9 / S10 用分钟线根本做不了**——它们是"必须上 tick/L2"的铁证，也是 §2 数据字典必须扩列的原因。S1 / S3 / S4 / S11 用 3 秒盘口快照可做但精度受限。
2. **S5 / S8 / S12 与行情无关，是执行与系统层的**——不管数据多好，没有这三个，前面十个的"动作"都只是愿望。
3. 每个子策略的阈值都标 ⚠️，与主策略同样纪律：先做分布统计再定，禁止拍脑袋。

### 3.7 集合竞价段 ⭐（原策略完全缺失，本轮补全）

> 原策略的时间轴从 09:30 开始，但 A 股 09:15–09:25 的集合竞价是短线最关键的信息窗口之一，且**开盘价在 09:25 就已确定**，09:30 才能交易——中间 5 分钟是纯观察窗。

| 时刻 | 市场规则 | 策略动作 |
|---|---|---|
| 09:15–09:20 | 可挂单**可撤单** | **只观察不决策**。此段的竞价量/价含大量虚假撤单诱骗，不得作为信号输入 |
| 09:20–09:25 | 可挂单**不可撤单** | 竞价数据开始可信。计算竞价量比、竞价涨幅 |
| 09:25 | 集合竞价撮合，**开盘价确定** | 立即计算：`open` vs `POC_yest`、`open` vs `pre_close` |
| 09:25–09:30 | 静默期（不可交易） | 决策窗：预判 A5（低开破 POC → 开盘即清仓）；标记高开 >5% 的票禁止加仓 |
| 09:30 | 连续竞价开始 | 执行 09:25–09:30 定下的动作 |

**新增规则**：
- **一字板买入排队**：若某只 L1 票在 09:15 即一字涨停，本策略 **C4 禁止买入**（原策略已有），故不排队。
- **竞价量比过滤**：⚠️待定——`竞价成交额 / 昨日全天成交额 > 5%` 可能是异动信号，需在 P2 验证是否有增量价值。
- **高开 >5% 处理**：持仓票禁用 09:30–10:30 的任何加仓；新信号票当日不进 L2（追高风险）。
- **低开 >5% 且开盘价 < POC_yest**：直接触发 A5，09:30 开盘即清仓。

### 3.8 极端场景与风控熔断

#### 3.8.1 涨跌停价的精确计算（原策略未定义，差 1 分钱就判错）

```
涨停价 = round_half_up(pre_close × (1 + limit_pct), 2)
跌停价 = round_half_up(pre_close × (1 − limit_pct), 2)
```

- `pre_close` 必须用**不复权**昨收
- 四舍五入到 0.01 元（**不是截断**）
- `limit_pct` 分档：

| 板块 | 幅度 | 判定方式 |
|---|---|---|
| 主板（沪 60x / 深 00x） | 10% | 代码前缀 |
| 创业板（300/301） | 20% | 代码前缀 |
| 科创板（688/689） | 20% | 代码前缀 |
| 北交所（8xx/920） | 30% | 代码前缀 |
| ST / *ST（任意板块） | 5% | **必须查股票名称含 ST**，不能只看代码 |
| 新股上市前 5 个交易日 | 无涨跌幅限制 | 需上市日期字段 |

> ⚠️ 上述规则请在 P0 用交易所现行规则原文复核一遍再写进代码。规则会变（印花税、涨跌幅都改过），**代码里不得硬编码，必须从配置读**。

#### 3.8.2 大盘熔断（原策略含糊，此处定死）

原文：「大盘跌 >2% 且放量下杀 → 冻结买入」。「放量」多少？用哪个指数？什么时候解除？全部未定义。

**修补规则**：
- **指数**：取 `上证指数` 与 `创业板指` 中**跌幅更大**的那个（持仓多为创业板票时创业板指更相关）
- **触发**：`index_pct < −2.0%` 且 `index_amount_todate ≥ 1.2 × 同时刻20日均量`
- **动作**：
  1. 冻结所有 S0 → S1（不再产生新买入信号）
  2. 所有持仓的止损线上移至 `max(现止损线, 今日 VAL)`
  3. **不强制平仓**（避免在恐慌底部割肉）
- **解除**：当日**不解除**。次日 09:30 重新评估。
- **日志**：熔断触发/解除必须推送通知并落库，回测时可复现。

#### 3.8.3 停牌与临停

| 场景 | 处理 |
|---|---|
| 盘中临时停牌（持仓股） | 状态冻结，止损/止盈全部挂起；复牌后 5 分钟内重新评估全部条件 |
| 全天停牌（持仓股） | 持仓保留，计入"冻结资金"；⚠️同时持有的停牌股上限建议 1 只 |
| 停牌超过 ⚠️5 个交易日 | 复牌当日无条件清仓（逻辑已失效） |
| 候选池股票停牌 | 立即降级至 L0，当日不再考虑 |

#### 3.8.4 一字板

- **一字涨停（想买）**：C4 禁止买入，不排队。
- **一字跌停（持仓）**：见 §3.6.4。

#### 3.8.5 收盘集合竞价（14:57–15:00）⭐ 原策略缺失

沪深两市自 2018 年起均设**收盘集合竞价**：

| 时段 | 规则 | 对策略的约束 |
|---|---|---|
| 14:57–15:00 | 集合竞价，**只能挂单，不能撤单**，无连续竞价 | **此时段内无法按市价即时成交** |

**后果**：任何写着「14:5x 清仓」的规则，若时刻晚于 14:57，实际执行方式与预期完全不同——不是"以当时价格卖出"，而是"挂单参与收盘撮合，成交价 = 收盘价，且挂出后不可反悔"。

**死规定**：
- 所有需要**即时成交**的动作（B1 硬止损、FLUSH 转市价）必须在 **14:56:30 之前**发出，否则顺延到次日；
- 所有**尾盘定型**动作（C2 清仓、C5 清仓）统一定在 **14:50**，留足缓冲；
- 回测引擎必须把 14:57–15:00 建模为"只能以收盘价成交"，不得按分钟 K 线的 open 成交。

#### 3.8.6 除权除息对持仓的影响 ⭐ 原策略缺失

持仓期间个股除权除息（送转、派息），价格会**非连续跳变**。若不处理，止损线会被立刻误触发（比如 10 送 10，价格腰斩，任何止损线都被"跌破"）。

**规则**：
- 除权日开盘前，所有该股的价格型状态量按除权因子等比调整：`stop_price`、`POC_yest`、`AVP_POC`、`C_POC/VAH/VAL`、`LVN 位置`；
- 持仓股数按送转比例调整；
- **除权当日不产生新的买入信号，且暂停止盈规则**（只保留硬止损，且按调整后的价位判定）；
- 跨日 VP 从除权日重新起算（见 §2.3）。

#### 3.8.7 同票当日去重

同一只股票**当日最多产生 1 次买入信号**（不论是否被仓位约束挡下）。避免同一逻辑在缓冲带内反复触发。
rQuant 的 surge-watch 已采用同样的 once-per-stock-per-day 规则，此处沿用。

## 5. 回测底座契约（Backtest Engine Contract）

> **这一节的所有内容对 AI 助手只读。** 参照视频里「AI 只改研究模块，不改成交规则」的原则。
> 允许修改本节的唯一方式：人工 review + 在 `experiment_log` 里记录修改理由，并**重跑全部历史实验**。

### 5.1 成交假设

| 项 | 规定 |
|---|---|
| 信号计算时刻 | 分钟 K 收盘后（`available_at` 见 §2.2） |
| 最早成交时刻 | **信号时刻的下一分钟开盘价** |
| 成交价 | 下一分钟 `open`；若形态 A（人工执行），另跑一版用「信号后 3 分钟 VWAP」做敏感性 |
| 涨停时买入 | **不可成交**（`bid1_price == limit_up` 时买单不成交） |
| 跌停时卖出 | **不可成交**，顺延到次日 |
| 停牌 | 不可成交，持仓冻结 |

### 5.2 交易成本（写死，不允许"为了让结果好看"而调低）

| 项 | 数值 | 方向 |
|---|---|---|
| 佣金 | ⚠️万 2.5（按实际券商填），单笔最低 5 元 | 双边 |
| 印花税 | 0.05%（⚠️以现行规定为准） | **卖出单边** |
| 过户费 | 0.001% | 双边 |
| 滑点 | **2 个最小变动价位（tick）**，即 0.02 元 | 双边 |

> **滑点用 tick 数而不是百分比**：A 股最小变动 0.01 元，3 元股的 1 tick = 0.33%，300 元股的 1 tick = 0.003%。用百分比会系统性低估低价股的摩擦成本。

### 5.3 组合规则

| 项 | 数值 |
|---|---|
| 总仓位上限 | 80% |
| 单票仓位上限 | 20% |
| 最大同时持仓 | 4 只 |
| 卖出资金当日可用 | 是（A 股资金 T+0） |
| 初始资金 | ⚠️按实际填，且必须跑 3 档做容量测试 |

### 5.4 容量限制（原策略未评估）

单票买入金额不得超过该股 **当日成交额的 0.5%**，否则冲击成本失真。

推论：单票 20% 仓位下，账户规模上限 ≈ `个股日成交额 × 0.5% / 20%` = `日成交额 × 2.5%`。
若候选池个股日成交额中位数为 1 亿，则账户上限约 250 万。**超过这个规模，回测结果不可信。**

### 5.5 Point-in-Time 股票池（防幸存者偏差）

回测在任意历史日 T 使用的股票列表，必须是**T 日当时真实在市的列表**，不是今天的列表。具体：

- 必须包含 T 日之后退市 / 被并购的股票（它们当时是可选标的，且往往是亏损来源）；
- 必须排除 T 日之后才上市的股票；
- ST 状态必须用 T 日当时的状态，不是今天的状态（ST 会摘帽也会戴帽，涨跌幅限制随之变化）；
- 流通市值、行业分类同理，必须是 T 日当时的值。

**实现要求**：股票基础信息表必须带 `list_date` / `delist_date` / ST 状态变更历史，查询时按 T 日过滤。若数据源只提供"当前快照"，则必须自行按日归档，**否则回测结论不可信**。

### 5.6 基准（不许只跟 0 比）

必须同时对比：
1. 同期沪深300 / 中证1000 等权持有
2. 同期创业板指
3. **同板块同市值同流动性的随机选股组合**（最重要的基准，能剥离掉"选到了小盘股"这个 beta）
4. 去掉 VP 条件、只保留"放量大阳线"的简化版策略（证明 VP 有增量价值）

## 6. 实验协议（Experiment Protocol）

> 在跑第一次回测之前定好。**跑完之后不许改。**

### 6.1 数据切分

| 集合 | 区间 | 用途 |
|---|---|---|
| 开发集 | ⚠️2021-01-01 – 2024-12-31 | 随便调参 |
| 验证集 | ⚠️2025-01-01 – 2025-12-31 | 每次只许看一次，看完记 log |
| **盲测集** | ⚠️2026-01-01 至今 | **全程锁定，只在最终决策前跑一次** |

> rQuant 现行纪律是「训练 ≤2025-12-31 / 验证 2026+」，本项目沿用同一切分口径以便横向对比。

### 6.2 实验纪律

1. **一次实验只改一个变量**。改两个就说不清是哪个起作用。
2. 每次实验必须先写「预期结果」再跑。跑完对比预期，**结果与预期不符时记录下来**——这比结果好看重要得多。
3. 失败的实验**必须记录**，不许删。删掉失败记录 = 自欺欺人的过拟合。
4. 累计实验次数 > ⚠️30 次后，验证集结果不再可信（多重检验问题），必须换新的盲测区间。

### 6.3 失败标准（Kill Criteria）—— 出现以下任一即判定策略无效

| # | 判定 |
|---|---|
| K1 | 信号频次 < 100 次/年 → 样本不足，统计上无法证明任何事 |
| K2 | 按 `score` 分 5 组，收益无单调性 |
| K3 | 验证集 Rank IC 或超额收益接近 0 |
| K4 | 收益集中于单一年份 / 单一板块 / 单一行情阶段（如只有 2024Q4 赚钱） |
| K5 | 扣除 §5.2 全部成本后超额收益消失 |
| K6 | 参数敏感：某参数 ±20% 导致收益变号 |
| K7 | 剔除收益最高的 5% 信号后，策略不再显著为正 |
| K8 | 相对 §5.6 的第 3 项基准（同板块随机组合）无显著超额 |

**K1 是第一道闸门，在写任何策略代码之前就能测。**（详见 §9 的 P0）

## 8. 工程可行性

> 本节全部结论基于 2026-07-27 的专项调研：tushare 官方文档 + SDK 1.4.29 源码逐行核实 + `hq.sinajs.cn` 本机实测 + rQuant 自身的生产事故记录。
> 凡标注「实测」的数字来自真实运行，凡标注「社区」的一律降级看待。

### 8.1 存储量（实测单行成本，非拍脑袋）

用真实结构（tick 对齐价格、100 股整手、按 code+time 排序）生成样本，实测 Parquet+zstd 落盘：

| 数据 | 实测单行 | 范围 | 日增量 | 年增量（244 交易日） | 判断 |
|---|---|---|---|---|---|
| 五档快照 @3s | **32.1 B** | 全市场 5400 | 0.83–1.30 GB | **200–320 GB** | 不可行 |
| 五档快照 @3s | 32.1 B | 候选池 200 | 31–48 MB | **7.5–11.7 GB** | 可行 |
| 五档快照 @3s | 32.1 B | 触发池 50 | 8–12 MB | **1.9–2.9 GB** | 轻松 |
| 1min K 线 | **15.8 B** | 全市场 5400 | 20.5–26.5 MB | **5.0–6.4 GB** | 可行 |
| 日线 | — | 全市场 5400 | ~0.5 MB | ~130 MB | 轻松 |

**去重可再砍约 2/3**：3 秒间隔下大量冷门票的盘口逐帧不变，只落「有变化的快照」时留存率估算约 37%，候选池 200 只可降到约 **2.8 GB/年**。⚠️ 留存率是估算，P3 需实测校准。

**云端现状（实测 `GET 82.156.0.68:8081/backup/latest.json`，2026-07-27）**：

| 项 | 值 |
|---|---|
| 云端只读副本 | **7.55 GB**，52 张表 |
| 压缩后 | 2.31 GB |
| `minute_bar` 行数 | **4750 万行**，覆盖 2025-03-28 至今 |
| `daily_bar` 行数 | 约 640 万行，回补至 2020-08-24 |
| 云盘可用空间 | 约 **63 GiB**（DEPLOY.md 记录，清理后） |

> **结论：存储不是瓶颈。** 即使按最激进的方案（候选池 200 只五档 + 全市场分钟线），年增量约 14–18 GB，云盘 63 GiB 可用空间能撑三年以上。
>
> ⚠️ **但云服务器的 CPU / 内存规格在任何文档里都没有记录**（`DEPLOY.md`、`docs/deploy/`、`README.md` 全无）。P0 必须补一条：ssh 上去跑 `nproc && free -h && df -h` 并写进 DEPLOY.md。

### 8.2 算力

- VP 计算本质是按价格分桶的 group-by 聚合，DuckDB 向量化引擎处理这个量级是秒级的。
- 复合 VP 必须**增量滚动**（每日加一天、减一天）。全量是 5400 × 60 × 240 ≈ 7.8 亿行，每天重算不现实。
- 盘中实时 Session VP 只对 L1 池（≤300 只）维护，单票当日最多 240 根分钟线，计算量可忽略。
- **瓶颈判断：不是 CPU，是数据获取的请求配额与 IP 信誉。** 见 §8.3。

### 8.3 数据源矩阵（本节是全文最重要的工程结论）

#### 8.3.1 一个结构性区分：tushare 的「实时」分两类，风险完全不同

| 类别 | 接口 | 数据实际从哪来 | 是否吃 IP 反爬 |
|---|---|---|---|
| **服务端 API**（token 认证） | `rt_min` / `rt_min_daily` / **`rt_k`** / `stk_mins` / `stk_auction` | tushare 自己的服务器 | **否**，限流走账户配额 |
| **客户端爬虫**（SDK 内置） | `realtime_quote` / `realtime_list` / `realtime_tick` | **你的机器直连新浪/东财/腾讯** | **是**，与自己写爬虫等价 |

> `ts.realtime_quote()` 名字挂在 tushare 下，源码（`tushare/stock/rtq.py`）里它只是用 token 验一下权限，然后直接 `requests.get('https://hq.sinajs.cn/...')`。**把它当作「付费了就不怕封 IP」是错的。**

#### 8.3.2 全矩阵

| 数据源 | 盘口 | 逐笔 | 云端可用性 | 年成本 | 封 IP 风险 |
|---|---|---|---|---|---|
| **tushare `rt_k`**（doc 372） | **买一/卖一价+量 + 成交笔数**，单次 6000 条覆盖全市场 | 无 | **优**，token 认证 | **¥2400** | **无** |
| tushare `rt_min` / `rt_min_daily` | 无 | 无 | 优 | ¥12000 | 无 |
| tushare `stk_mins` | 无 | 无 | 优 | ¥2000（单独） | 无 |
| tushare A 股 tick / L2 API | — | — | — | **不存在** | — |
| **新浪 `hq.sinajs.cn`** | **完整五档**；实测 890 代码/请求，全市场 7 个请求 | 另有端点，仅当日 | **中**，需 `Referer` 头，已被封过 | 免费 | **高** |
| 东财 `push2` | 五档，但**一票一请求** | 有，深度不确定 | **差** | 免费 | **很高** |
| AKShare `stock_bid_ask_em` | 五档（底层就是东财） | — | 差 | 免费 | 很高 |
| mootdx / tdxpy | 五档 + 历史逐笔 | 有 | **Linux 原生可用，但已实质停摆** | 免费 | 中 |
| iTick | 声称十档，档位不明 | 声称有 | 好 | ¥6800–27000 | 无（但无资质声明） |
| QMT / miniQMT | 有 | 有 | **不可用**（Windows-only） | — | — |
| Ptrade / 掘金 L2 | 有 | 有 | **不可用**（券商内网托管） | — | — |

**几条必须知道的硬事实**：

- **A 股逐笔 / 十档对零售 + Linux，没有一条既合规又稳定又便宜的路。** tushare 没卖（SDK 里那个 `HQ_STK_TICK` WebSocket topic 需要华锐 `tgw` 或华泰 INSIGHT 机构网关）；QMT/Ptrade/掘金锁在 Windows 或券商内网；交易所只对机构；社区转发服务是未授权二次分发。**本规格因此不依赖逐笔数据。**
- **mootdx 应从技术栈里降级。** 它在 Linux 上确实能拿五档和历史逐笔且免费，但代码两年无实质更新，且 [issue #157](https://github.com/mootdx/mootdx/issues/157)（2026-07-20，一周前，未修复）报告**全部 8 个公开节点返回空数据**。`CLAUDE.md` 技术栈表里给它的评级现在偏高，建议修订。
- **新浪五档的批量上限是 URL 长度约 8 KB，不是代码条数**（本机实测：890 个代码成功，900 个返回 HTTP 431）。全市场 5400 只只需 7 个请求。这个数字网上查不到。
- **东财不只按 IP 封，还对长连接进程指纹做识别**——rQuant 自己的代码注释（`panorama_data.py`，2026-07-06）记录了「同进程连续 RST、新进程三路秒通」的现象，必须强制每次新建 TCP/TLS。

#### 8.3.3 云端封 IP：rQuant 自己的四次事故就是证据

| 日期 | 事件 | 出处 |
|---|---|---|
| 2026-04-29 | `stock_zh_a_spot_em`（东财）被**腾讯云北京 IP 段**屏蔽；**同一时刻家庭 IP 正常** | commit `64142dd` |
| 2026-04-29 | dashboard K 线同样问题复现 | commit `898914d` |
| 2026-07-06 | **办公网 IP**（非机房）因多进程全天高频访问，被东财 + 新浪双风控，直连与 SOCKS 同时 RST，sina 返回 456 | CHANGELOG |
| 2026-07-07 | **云端 IP 被东财 + 新浪双双拉黑**，surge 零快照饿死，当日无推送 | commit `bc6208e` |

由此得到四条结论，全部是被验证过的、不是推测：

1. **IDC IP 与住宅 IP 待遇确实不同**（4/29 同一时刻云端挂、家里正常）。
2. **但住宅 IP 不是免死金牌**（7/6 办公网同样被封），触发因素是频率与并发。
3. **多源兜底不管用**（7/7 东财和新浪同一天一起封，三级路由全灭）。
4. **降频 + 缩池也不够**（4 月就定了「池子 ≤50、间隔 ≥3s」，7 月做全市场拉取照样被封）。

| 规避手段 | 评价 |
|---|---|
| **换 token 认证 API** | **唯一被本项目验证有效的根治方案**。`bc6208e` 就是这么做的 |
| 降频 / 缩池 | 有帮助但不充分，已被 7/7 证伪 |
| 多源切换 | 已被 7/7 证伪 |
| SOCKS 代理 | 试过，7/6 直连与 SOCKS 同时 RST |
| 住宅代理 | 国内动态住宅约 5 元/GB 起。按全市场五档 6.4 GB/日算约 **7700 元/年**，比 tushare 贵得多，且不解决合规问题 |
| 家宽 frp 反向隧道 | 原理成立（4/29 的证据支持），但**未搜到任何把 frp 用于行情反爬场景的公开案例**，属于没人踩过坑的路 |

### 8.4 全云端迁移的结论

| 维度 | 结论 |
|---|---|
| 存储 | **可行**。年增量 14–18 GB，云盘 63 GiB 余量能撑三年以上 |
| 算力 | **可行**，瓶颈在 IO 不在 CPU。⚠️ 但 CPU/内存规格无记录，P0 必须补测 |
| tushare 类付费接口（含 `rt_k` 盘口） | **可行**，零封禁风险 |
| 免费行情接口（新浪/东财）的五档 | **不可行**，已被四次生产事故验证 |
| 通达信协议（mootdx） | **不可行**，全节点自 2026-07-20 起返回空 |
| A 股逐笔 / 十档 | **不可得**（零售 + Linux 无合规路径），本规格已设计为不依赖 |

**推荐方案：全云端，走 `rt_k`。**

```
云端服务器（唯一运行环境）
  ├── tushare stk_mins / rt_min ──► 分钟线（现状，已稳定）
  ├── tushare rt_k ¥200/月 ──────► 全市场买一/卖一价量 + 成交笔数
  │     └── 封单量 = bid_volume1 where bid_price1 == limit_up
  ├── VP 计算 + 状态机 + 回测
  └── 告警推送（复用现有 PushDeer / PushPlus 通道）
```

这个方案**不需要家宽混合架构，不需要五档，不需要代理**，月成本 ¥200。

> **初稿的「家里 Mac 采集五档 + 上行云端」混合架构建议已作废**，理由有三：
> 1. 封单量只需要买一档，`rt_k` 就有；
> 2. rQuant 的本地主库已于 2026-07-27 全量迁云并删除，本地 `data/` 只剩 76 MB，本地已不再是数据的一极；
> 3. 引入家宽链路就必须处理断网降级、时钟同步、上行加密三件事，为了「五档比一档多四档」这点增量不划算。
>
> 保留一个前提：**如果 P4 实测发现买一档不足以刻画封板质量**（比如需要看委托队列判断封单是一笔大单还是很多小单），再重新评估五档，届时家宽方案可以捡回来。

⚠️ **P0 必须实测验证的三件事**（在为 `rt_k` 付钱之前）：
1. `rt_k` 的实际刷新频率——官方文档没写，可能不是 3 秒级；
2. `bid_price1` / `bid_volume1` 等字段需在 `fields` 里显式请求（`默认显示=N`），实测能否正常返回；
3. 涨停封板时 `bid_price1` 是否确实等于涨停价、`bid_volume1` 是否就是封单量（用一只当日封板股对照东财盘口人工核验）。

### 8.5 一个附带发现：本地热备当前处于失效状态

`logs/sync-from-cloud.log` 尾部显示**近 25 次 `curl` 全部超时失败**（`Operation timed out after 600001 ms`，每次拉到 5.7 亿 ~ 15.5 亿字节就断）。

这意味着 2026-07-27 全量迁云之后，**云端数据目前没有可用的本地热备**。这与本策略无关，但属于生产风险，建议单独处理。

## 9. 分阶段实施计划与 Kill Criteria

### 9.1 项目归属：同仓库，独立运行时（初稿结论已修正）

**初稿建议「新开项目」，核实代码后修正为：留在 rQuant 仓库内，但用独立的写库与独立的 systemd unit 做运行时隔离。**

改判的三条理由：

1. **VP 引擎已经在 rQuant 里了。** `volume_profile.py` 551 行，POC、价值区、支撑阻力、风控计划齐全，且已接入筛选与 paper 风控。新开项目意味着要么复制这份代码（两份实现必然分叉），要么远程调用（徒增复杂度）。
2. **封单的日频历史也已经在库里**（三张表，见 §3.6.1）。这些数据是 rQuant 每天在维护的，跨项目共享只会制造同步问题。
3. **本地主库已于 2026-07-27 全量迁云并删除**，本地 `data/` 只剩 76 MB。初稿设想的「新项目 ATTACH 本地 `rquant_ro.duckdb` 只读副本」这个方案，**前提已经不存在了**。

**但运行时必须隔离**，因为 DuckDB 单文件写锁是 rQuant 已经出过生产事故的地方：

```
rQuant/（同一个仓库）
├── src/rquant/                    生产代码（monitor / surge_watch / daily）
│   ├── volume_profile.py          ← 复用并增量改造（见 §3.3.4）
│   ├── adapter/tushare.py         ← 新增 rt_k 方法
│   └── notify/                    ← 复用推送通道
│
├── src/rquant/vp/                 新增子包，本策略全部代码
│   ├── engine/                    🔒 回测底座，AI 只读（见 §7）
│   └── sandbox/                   ✍️ 研究沙盒，7 个可写文件
│
└── data/
    ├── rquant.duckdb              生产写库（monitor / daily 写）
    ├── rquant_ro.duckdb           只读副本，5 min 刷新
    └── rvp.duckdb                 ← 新增：本策略的独立写库
                                     （VP 表、盘口快照、状态机、实验日志）
                                     只读 ATTACH rquant_ro.duckdb 取日线/基础信息
```

**隔离清单（缺一条就会重演写锁事故）**：
- 独立写库 `rvp.duckdb`，绝不写主库
- 读主库一律 `ATTACH ... (READ_ONLY)` 挂只读副本，不碰 `rquant.duckdb`
- 独立 systemd unit，与 `rquant-monitor` / `rquant-daily` 的时间窗错开
- 独立的 notify scene（新增 `vp_signal`），不复用 `price_level`
- 独立的 CLI 命名空间（`rquant vp-*`）

**需要修订 `CLAUDE.md` 的一条边界**：现行「明确暂时不做 Level2」需要加一条说明——买一档挂单量（Level-1 范畴）用于封板质量判断属于例外，逐笔与十档仍然不做。**这是一次有理由的、显式的边界修订，不是无声扩张。**

### 9.2 阶段计划（因封单日频历史已在库，顺序有调整）

**最重要的两道闸门仍然是 P0 和 P2**——花时间最少，否定得最彻底。

> **P0 为什么用日线代理而不是分钟线**：云端 `minute_bar` 覆盖 2025-03-28 至今，约 16 个月。按开发/验证/盲测三段切分，每段不足 6 个月，统计功效严重不足。而 `daily_bar` 已回补至 2020-08-24，足以先回答那个最该先问的问题：**这套条件一年到底触发几次？**
