01

先看懂这张图

成交量分布（Volume Profile，简称 VP）把成交量按价格堆起来，而不是按时间。横着的每一根柱子代表「在这个价位上一共成交了多少钱」。柱子越长，说明越多人在这个价位换过手。

这跟通达信里的「筹码峰」不是一回事：筹码峰是按换手率衰减模型推算出来的持仓成本，VP 是真实发生过的成交统计。

原讨论最致命的缺口就在这里。整套策略反复用 POC、VAH、VAL、LVN 做买卖点，但从头到尾没有一处定义它们怎么算——价格分几档？一分钟的成交量怎么摊到各个价位？价值区从哪边开始扩？没定义就意味着两个人写出来的代码结果不同，回测和实盘必然分叉。

好消息：这部分不用从零写。rQuant 里已经有一个 551 行的 volume_profile.py，POC、价值区、支撑阻力候选、风控计划都有，而且已经接进了筛选和模拟盘风控。要做的是增量改造，不是重建：

  • 价格分档现在固定 0.01 元 —— 3 元股和 300 元股不可比，要改成按价格比例自适应
  • 价值区算法不标准 —— 见缺口 G20，双峰形态下会系统性拉宽
  • 盘中实时的单日 VP、锚点 VP、LVN —— 这三样是真的没有，要新增
  • 复权处理已经有了，而且区分了「可比股数」和「原始成交额」双口径，比我原本设想的还细
02

策略的一天

点任意时刻，看系统那一刻在做什么、能做什么、不能做什么。

原讨论的时间轴从 09:30 开始，前后各少一截。开头少了集合竞价（09:15–09:25）——开盘价其实 09:25 就定了，09:30 才能交易，中间那 5 分钟是纯决策窗；结尾少了收盘集合竞价（14:57–15:00）——那三分钟只能挂单不能撤单，也没有连续竞价，任何写着「14:58 清仓」的规则实际执行方式跟预期完全不同。

03

四级订阅池

本轮补全

这是你问的第一个缺口。原策略默认「随时能看到任意股票的实时数据」，但不同数据的获取成本差三个数量级。不分级不是不优雅，是根本跑不起来——下面点开 L2 看那个数字。

订阅分级是可行性前提，不是优化项。全市场 5400 只每 3 秒存一次五档盘口 ≈ 250 GB/年，单机直接出局；只对触发池 30 只存 ≈ 1.5 GB/年，轻松。同一套策略，差别只在于有没有订阅生命周期。

订阅管理的六条工程硬要求

要求说明
幂等subscribe(code, level) 重复调用无副作用
持久化订阅表落库，不只在内存。重启后按库重建——rQuant 的 surge-watch 就因为累计量只在内存，重启后归零丢了一整个早盘
TTL 兜底每条订阅带过期时间，最长到当日 15:00，防止「只增不减」的订阅泄漏
退订 ≠ 删数据退订只停止新数据流入，已落库的历史一律保留
配额预算启动时算出当日最大请求数与数据源配额比对，超出则拒绝启动并报警，不能盘中才发现打爆
降级留痕主数据源失败切备用时必须记日志并在信号上打标——用降级数据产生的信号可信度不同，不能静默降级

升降级的防抖设计

价格在阈值附近来回抖动会导致同一只票每分钟升降级几十次，打爆配额。所以升级和降级用不同的阈值（滞回），并且降级后有冷却期。

动作条件阈值
L1 → L2 升级价格进入昨日 POC 缓冲带±1.5%
L2 → L1 降级脱离缓冲带（宽于升级线）±2.5%
降级确认时长连续脱离多久才降30 min
降级后冷却多久内不得再升级15 min
L2 池上限超限按接近度挤掉最远的，并记录被挤掉的数量30 只
04

买入判定

六个条件同时满足才买。时间窗锁定在下午——因为 A 股是 T+1，当天买了当天不能卖，越晚买承担的当日波动风险越小。

#条件精确表达
E1时间窗13:30 ≤ now ≤ 14:30
E2回踩昨日筹码峰|P − POC_yest| / POC_yest ≤ 0.8%
E3抛压衰竭（缩量）V_5m_prev < 0.6 × V_5m_avg20
E4未临近涨停P < limit_up × 0.98
E5大盘未熔断见风控
E6仓位有空间持仓 < 4 只 且 总仓位 < 80%

E3 藏着一个必然出错的未来函数。原文写的是「当前 5 分钟成交量 < 0.6 × 平均」。可是在 13:31 判定时，「当前这根 5 分钟」才走了 1 分钟，成交量天然只有五分之一——它会把每一根 5 分钟 K 线的开头都判成缩量。

修法只有两种，必须二选一写死：用最近一根已经收完的 5 分钟；或者用当前根按时间比例归一（V / (已过秒数 / 300)），并且字段名里必须体现出来。

还有一个原文完全没写的分支

如果同一时刻冒出 5 个信号，但只剩 2 个仓位，买哪两个？原策略没有答案。没有打分函数，代码就会退化成「按股票代码顺序」——那意味着回测结果不可复现，而且系统性偏向 000 开头的票。

score = w₁ × 贴近 POC 的程度
      + w₂ × 缩量的程度
      + w₃ × 突破复合 VP 上界的幅度分位
      + w₄ × 贴近主力锚点成本的程度

先用等权跑通，权重留到 P2 阶段用数据标定。不要一上来就调权重——那是在还没证明策略有效之前就开始过拟合。

05

持仓管理决策矩阵

T+1 制度下，买入的仓位从次日 09:30 起可卖。把一天切成三段，每段的分支必须互斥且穷尽——任何两条规则同时适用，或者任何一种价格走势没被覆盖，程序就会做出意料之外的操作。

原策略在这里有两处分支漏洞，本轮已修补。

其一，A4「未涨停且突破不了昨日价值区上界就卖 50%」和 A5「跌破昨日 POC 就清仓」在价格处于两线之间时同时部分适用，而且原文没说 A4 是 09:31 就判还是 10:30 才判——修法是把 A4 定为「10:30 这一个时点判一次」，A5 为「全时段持续监控且优先级更高」。

其二，尾盘只写了 3 个状态，漏掉了「收在 POC 与 VAH 之间」和「收在 POC 之下但白天没触发过止损」两种真实会发生的情况。

06

封单量监控与条件单

本轮补全

这是你问的第二个缺口，而且指得很准。原策略在这里只有一句「触及涨停但炸板放量 → 卖 50%」——「炸板」没定义，「放量」没定义，整个封板质量监控体系是空的。而在 A 股短线里，封板质量比涨停本身重要得多。

先把三个词定死

状态可执行定义
封板bid1_price == limit_up 且 seal_vol > 0
炸板曾封板，之后 last_price < limit_up 且持续 ≥ 10 秒
回封炸板后重新封板，且封单额 ≥ 炸板前的 50%

那 10 秒是防止一笔大单瞬间砸穿后立刻回封被误判成炸板。另外「当日炸板次数」必须落库计数——炸板 2 次及以上的票当日直接拉黑，这个概念原策略里完全没有。

为什么预警时是「挂涨停价排队」而不是直接砸盘。封板的时候涨停价上还压着巨量买单，这时挂涨停价卖出能立刻成交且一分钱不让。等封单真崩了再挂，前面已经排了几千手，根本轮不到你。这是 A 股涨停板机制里的一个具体优势，原策略完全没利用。

数据这一关比原先判断的好走得多。我初稿以为封单监控必须要五档盘口，云端拿不到就得整节砍掉。核实之后发现判断错了：

封单量的定义是「买一价等于涨停价时的买一挂单量」——买一价量属于 Level-1 范畴，不是 Level-2。而 tushare 有一个叫 rt_k 的接口（¥200/月），单次调用 6000 条就能覆盖全市场，返回买一/卖一的价和量，外加开盘以来的成交笔数，而且是 token 认证——完全不吃 IP 反爬。这条路在初稿里被整个漏掉了。

更省事的是，封单的日频历史已经在 rQuant 的库里了：limit_list_daily 有封单金额和开板次数，limit_up_pool_daily 有封板资金和炸板次数，kpl_list_daily 有封单量和最大封单。这意味着「封单强度到底能不能预测次日收益」这个问题，用现成的日频数据就能先验证一遍，不用先花钱接实时。

仍然成立的红线：绝不用分钟线去「猜」实时封单量。日频历史用来验证因子有没有用，实时数据用来盘中执行，两者不能互相替代。硬凑一个「近似封单量」出来，会得到一个看起来能跑、实际全是噪声的指标。

07

全部 20 个缺口

你问「类似的缺漏不确定是否还有」。有，一共 20 项——其中 1 项不是原讨论的问题，而是核实代码时在 rQuant 现有实现里发现的。致命指不补就写不出可复现的代码；重要指不补会导致回测与实盘分叉；次要指影响收益但不影响正确性。

存储不是瓶颈，请求配额和 IP 信誉才是。但有一件事必须补：云服务器的 CPU 和内存规格在任何文档里都没有记录——DEPLOY.md、docs/deploy、README 全无。P0 得 ssh 上去跑一次 nproc && free -h && df -h 补进部署文档。

算力：瓶颈不在 CPU

VP 计算本质是按价格分桶的 group-by 聚合，DuckDB 的向量化引擎处理这个量级是秒级的。真正的瓶颈是数据获取的网络 IO 和 API 限频。

唯一需要小心的设计点：60 日复合 VP 必须增量滚动（每天加一天、减一天），不能每天全量重算——全量是 5400 只 × 60 天 × 240 根 ≈ 7.8 亿行。

接口封禁：已经用生产事故验证过了

推荐方案：纯云端，走 rt_k

云端服务器（唯一运行环境）
  ├─ tushare stk_mins / rt_min ──► 分钟线（现状，已稳定）
  ├─ tushare rt_k ¥200/月 ──────► 全市场买一/卖一价量 + 成交笔数
  │     └─ 封单量 = 买一价等于涨停价时的买一挂单量
  ├─ VP 计算 + 状态机 + 回测
  └─ 告警推送（复用现有通道）

不需要家宽混合架构，不需要五档，不需要代理，月成本 ¥200。

我初稿建议的「家里 Mac 采集五档、加密上行云端」这套混合架构作废，三个理由：封单量只要买一档而 rt_k 就有；rQuant 的本地主库已在 2026-07-27 全量迁云并删除，本地 data/ 只剩 76 MB，本地已经不再是数据的一极；引入家宽链路就得处理断网降级、时钟同步、上行加密三件事，为了「五档比一档多四档」这点增量不划算。

保留一个前提：如果 P4 实测发现买一档不足以刻画封板质量（比如需要看委托队列区分「一笔大单」还是「很多小单」），再重新评估五档，届时家宽方案可以捡回来。

顺带发现一个跟本策略无关、但属于生产风险的事：本地热备当前是失效的。logs/sync-from-cloud.log 尾部显示近 25 次同步全部超时失败（每次拉到 5.7 亿～15.5 亿字节就断）。也就是说 07-27 全量迁云之后，云端那 7.55 GB 数据目前没有可用的本地备份。建议单独处理。

09

分阶段计划与闸门

每个阶段都有一道不过就停的闸门。最重要的是 P0 和 P2——它们花的时间最少，否定得最彻底。

P0 为什么用日线代理而不是分钟线。云端 minute_bar 覆盖 2025-03-28 至今，约 16 个月。按「开发集 / 验证集 / 盲测集」三段切分，每段不足 6 个月，统计功效严重不足。而日线已经回补到 2020-08-24，足以先回答那个最该先问的问题：这套条件一年到底触发几次？如果一年不到 100 次，样本量根本证明不了任何事，项目直接终止，省下后面十几周。

这个做法 rQuant 已经验证可行——爆量因子那次就是用日线代理跑了 25 个交易日、2097 条信号，把「前几日无爆量」这个听起来很有道理的因子直接证伪了。

10

需要你拍板的三件事

D1
交付形态：信号提醒，还是全自动实盘？

决定整个系统的严格程度。信号提醒意味着执行价与信号价必然有偏差，回测必须建模「信号后 N 分钟的成交价」；全自动实盘需要券商接口，mac 环境下选择极少，且合规与资金风险陡增。建议信号提醒。

D2
封单监控的数据从哪来？

建议接 tushare rt_k，¥200/月。这个选项在我初稿里被完全漏掉了——当时以为必须要五档，而云端拿不到五档，于是只能在「砍掉封单监控」和「先解决数据源」之间二选一。实际上封单量只需要买一档，rt_k 一次调用就能拿全市场，还不吃 IP 反爬。

而且不急着付钱：封单的日频历史已经在库里，P2 就能先用它验证这个因子到底有没有用，验证通过再买。

D3
项目归属：塞进 rQuant，还是新开一个？

建议留在 rQuant 仓库内，但用独立的写库和独立的 systemd unit 做运行时隔离。

这里我改了主意。初稿判断是「新开项目」，理由是这套策略占了 rQuant 三条禁区。核实代码之后发现不成立：rQuant 早就在算 VP 了（volume_profile.py 551 行，POC、价值区、支撑阻力、风控计划齐全，已接入筛选）；封单的日频数据也早就在库里；而且本地主库已在 07-27 全量迁云删除，初稿设想的「新项目 ATTACH 本地只读副本」这个方案，前提已经没了。

新开项目意味着要么复制 VP 代码（两份实现必然分叉），要么远程调用（徒增复杂度）。但运行时必须隔离——独立写库 rvp.duckdb、只读 ATTACH 主库副本、独立 systemd unit 错开时间窗、独立通知场景、独立 CLI 命名空间。这五条缺一条就会重演 DuckDB 写锁事故。

代价是 CLAUDE.md 的边界守则要修订一条：买一档挂单量（Level-1 范畴）用于封板质量判断属于例外，逐笔和十档仍然不做。这是一次有理由、写明白的边界修订，不是无声扩张。
