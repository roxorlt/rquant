# 选股器第一条真实使用路径

> 对应已确认的 React 投研平台 v2 计划 C4.1。此页记录当前纵向切片的边界；原型和差距表的其余功能继续按总计划迭代。

## 用户路径与验收

用户打开「选股器」，从中文条件目录添加或删除条件、填写参数、选数据日期，然后运行筛选。页面展示每条条件后剩余的股票数、总命中数和分页结果；点击股票打开现有个股详情。修改条件或数据日期后，旧结果明确标为待重新运行，不继续冒充新结果。数据未发布、日期无数据、参数错误和筛空时，页面分别给出简短、可操作的中文反馈。手机宽度下，条件编辑和结果表仍能操作；技术字段、数据代编号和服务代号不进入正文。

现有 `nl_screen_universe` 在生产来源中主要发布当前日（`[0]`）字段，尚未发布所有历史偏移列和窗口聚合列。26 条注册规则仍全部列入中文条件目录，但目录可见不等于当前数据代能执行所有参数组合。遇到缺少所需字段的条件时，筛选必须拒绝并用简短中文说明，不能展示伪结果或把内部字段名放进正文。C4.1 在生产数据补齐这些列、26 条规则的参数组合实际可运行前保持「部分」。后续数据切片须补齐历史偏移和窗口聚合列，并用已发布数据代逐条验证规则与旧域筛选输出一致。

本切片要用真实 Serving 数据代和现有 26 条规则，不用原型的模拟筛选。此次先完成手工条件与结果阅读；自然语言解析、排名权重、保存池子、画布联动、盘中条件和公式导入按 v2 计划后续切片完成。尚未接通的按钮不出现在可操作区域。

## 设计选择

1. **复用域能力**：规则与参数校验来自 `rquant.llm.registry` / `ScreenPlan`；筛选和逐条命中复用 `screen_nl_projection` / `paginate_nl_screen_projection`。若旧 `build_rules` 的存储依赖妨碍网页 API 的导入隔离，把纯规则编译提取到域层，再由旧入口与网页共用。网页 API 不重新实现规则，React 不计算命中数。
2. **薄 API 契约**：`GET /api/v1/screen/blocks` 返回 26 条规则的中文短名、参数表单元数据与提示；`POST /api/v1/screen/run` 接受受限的结构化方案，返回数据日期、累积命中、结果行与游标。游标续页绑定原查询与数据代；原数据代不可用时返回需要重新运行的状态。Pydantic 是接口类型源头，生成 OpenAPI 和 TypeScript 类型。
3. **页面职责**：React 只维护表单草稿、运行中/结果/错误状态，调用统一 API hooks，用现有表格、空状态、提示和个股抽屉组件。条件目录和参数名称由后端提供中文文案；用户无需编辑 JSON 或看到 Python 名称。

直接在浏览器筛选会复制 Python 规则并使数据时点难以保证；另建一套服务端筛选引擎也会制造第二套业务语义。因此采用以上复用路径。所有读取固定在已发布的只读数据代，API 不直连 DuckDB 主库。

## 验证与边界

- 用合成数据代证明规则顺序、参数校验、逐条命中、无结果、续页、数据代变化后的处理；与已有筛选域函数输出一致。
- 证明当前数据代不支持的规则参数组合收到简短中文解释，页面不把错误筛选结果当成成功。
- 用浏览器用例验证添加/删除条件、运行、改条件后的旧结果提示、翻页、个股详情和 390 px 布局；检查正文无内部术语。
- 只运行受影响的 Python、Vitest、浏览器用例及仓库要求的 build/dist/API 类型门禁。写入与生产切流不在本切片内。
