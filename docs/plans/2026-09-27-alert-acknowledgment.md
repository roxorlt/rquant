# 告警确认与未确认数：实施边界

对应原型盯盘页的「确认」和总览未确认数，以及 v2 C12.2。本片只完成确认链路；规则编辑、测试推送和正式推送切换分别实现。旧推送记录的真实来源是 `logs/notification_log.jsonl`，不是旧版 DuckDB 表；它在时间线中表示一次通道提交，不能再当作第二条需要确认的告警。

**分级：高风险。** 确认会改变跨页面共享状态，并影响用户是否继续处理告警；错误计数或丢失确认会误导操作。实现前以本文件冻结失败模型，最终候选做一次独立审查，复核只限阻断项与修复回归。当前文档为实现边界，正式 SPEC 审查仍待完成。

## 资产、信任边界与不变量

- 资产：已发布的信号、盯盘触发和爆量事件；确认人的身份和时间；PageControl 命令回执；不可变 Serving 数据代；盯盘与总览的未确认数。
- 浏览器只提交事件身份、所见数据代和稳定命令 ID。网页 API 从一次借用的 Serving 数据代核对事件确实存在且允许确认，`current_user` 取 nginx 覆写的身份，并执行同站 JSON/CSRF 校验。不能信任浏览器传来的确认人、事件内容或状态。
- PageControl 是唯一确认状态写者，使用其受控命令与持久 SQLite 状态；网页和 Serving 均不写 DuckDB 主库或确认状态。Serving 发布器从该状态读一份有界快照，与事件源一起生成新代。各层只传有类型的必要字段，不传原始推送目标、错误或凭据。
- **触发事件才计入待确认**：`signal`、`monitor_event`、`surge_event` 可确认；`legacy_notification` 和 `deliveries` 是投递事实，无确认按钮，也不重复计数。未来新增告警类型须显式加入可确认白名单。
- 稳定 `alert_id` 由已发布事件的来源类型及规范化内容生成；相同事件跨数据代身份相同，实质变更得到新身份。盯盘表的 `(trade_date, ts_code, level)` 只保证单日唯一，身份还须绑定触发时刻和展示所依据的值；爆量身份也绑定确认时刻和内容。绝不以列表位置、页码、展示文案或客户端时间认定事件。
- 确认为全局处理状态，持久记录首位确认人、确认时刻和命令 ID；同一 `alert_id` 重复提交幂等，不覆盖首个记录。命令 ID 重放同一内容返回原结果，换内容拒绝。状态不得因来源短时缺失、Serving 换代或进程重启丢失。
- 正式启用时设置确认起点 `activated_at`。起点以前的历史事件可看，但不倒灌到未确认数。配置缺失、确认投影未发布或源不完整时，不显示精确的 0，不提供貌似可用的确认按钮；说明「确认状态暂不可用」。首次启用时间与生产配置变更另走授权流程。
- 成功命令回执只证明确认已持久化，并返回实际生效的首个确认 ID；重复确认也返回该已有 ID。新 Serving 代按 `alert_id` 和实际生效的确认 ID 看到确认行后才显示「已确认」，不能等待重复请求自己的命令 ID。同步期间显示「已受理，正在同步」，不可把旧代的总览数当新数。浏览器失联或回执含糊时保留原命令 ID 重试，不生成新确认。
- 未确认数覆盖最近 30 个自然日、确认起点之后的全部可确认事件，且只在所有参与来源与确认表完整、同代核对时给精确值。来源部分不可用时返回未知/部分状态，不把缺失当 0；时间线翻页和总览必须使用同一口径。

## 失败路径与聚焦验收

| 失败路径 | 必须看到的行为 |
|---|---|
| 伪造事件、投递记录、过期数据代或跨站请求 | 网页 API 拒绝写入，PageControl 状态不变；技术详情不进入页面正文。 |
| 同一命令重试、两个用户确认同一事件、命令 ID 换内容 | 只有一个持久确认；重试取回原结果，冲突明确拒绝。 |
| PageControl 写后响应丢失或进程崩溃 | 以原命令 ID 查询/重试能恢复状态；页面不提前宣布「已确认」。 |
| 事件内容修订、Serving 换代、确认投影滞后 | 旧事件身份不错误确认新内容；新代未包含回执时保持同步中，数值不伪精确。 |
| 确认文件不可读、状态表缺失、某事件源不可用 | 盯盘和总览都显示来源/确认状态不完整，不给精确 0。 |
| 历史 30 日事件多于页面首屏 | 未确认数来自全窗口有界来源，不以当前页长度计数；分页稳定且不重漏。 |

## 实施次序与接口

1. **身份与纯状态规则**：在 `src/rquant/alert_ack.py` 定义有界、规范化的事件身份与确认窗口规则；用真实形状的三种触发事件、内容修订、时区和重复键测试。通知记录和投递回执必须被排除。
2. **唯一写者**：在 `src/rquant/page_control.py` 增加 `ack_alert` 命令和事务内幂等确认表；确认起点作为受控配置/状态，补写后丢响应、崩溃重放、双人竞争测试。不得让网页直写状态文件或 DuckDB。
3. **发布与读模型**：在 Serving 契约和页面投影源新增有界确认投影及起点，核对状态行数、唯一性和事件身份；旧代无表明确为「尚未发布」。新旧投影在同一不可变数据代中消费。
4. **网页合同**：`POST /api/v1/monitor/ack` 接受 `command_id`、`generation_id`、`alert_id`，返回持久命令状态；GET 时间线增加每条可确认事件的状态和全窗口未确认数/完整性，不暴露原始身份给页面正文。总览复用同一读模型，避免另算一套。
5. **React 路径**：盯盘时间线逐条确认，提交中禁重入；成功回执显示同步中，换代核对后显示已确认。总览未确认数与时间线同口径；桌面、390px、键盘焦点、空态、失败和换代路径都做浏览器验证。文案短句，细节进提示。

验收需从本地合成但真实格式的事件源与 PageControl 状态，经 Serving 发布、网页 API 到两个 React 页面走通；同时覆盖上述失败表。正式约 10 GB 副本资源、生产配置、数据发布及入口切换另验证。此片通过仍不代表 M12 全部完成或可停旧 monitor。
