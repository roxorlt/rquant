# 盘中实时分钟与集合竞价迭代路线图

**目标：** 围绕 N 字战法，建立一个“不站在未来看过去”的盘中监控与模拟盘闭环。先接入集合竞价和 A 股实时分钟，所有盘中因子都按当时那一分钟已经可见的数据计算。

**总体架构：** 历史回测和未来盘中监控必须共用同一套特征语义。盘中循环负责每分钟拉数据、更新状态、判断信号、写模拟盘事件；收盘后任务负责回补历史、预计算慢特征、复盘收益。DuckDB 仍是主存储，常驻写入进程只写主库，Streamlit 读取只读副本。

**技术栈：** Python 3.11+、Tushare Pro、DuckDB、Streamlit、APScheduler/systemd、PushDeer/PushPlus、pandas。

## 2. 无未来函数原则

历史回测里的每一分钟，都必须模拟当时真实盘中的可见信息。

### 2.1 同分钟历史基准

今天 `10:07` 只能和过去 N 天的 `10:07` 比。

不能拿今天 `10:08` 之后的数据参与判断。

### 2.2 截至当前分钟的累计基准

比如当前是 `09:45`，只能用：

- 今天 `09:30-09:45` 的累计成交额。
- 过去 N 天 `09:30-09:45` 的累计成交额中位数。

不能用全天成交额。

### 2.3 日内加速度

当前分钟可以和之前已经发生的 `5/10` 分钟比较。

但 `09:30-09:32` 要单独处理，因为开盘前三分钟天然放量，不能直接套普通滚动窗口。

### 2.4 买入成交口径

如果信号在第 `t` 分钟收完后确认，模拟买入价用下一分钟开盘价。

不能在已经看完第 `t` 分钟的 high/low/close 后，还假装按第 `t` 分钟 close 买入。

### 2.5 日级别环境数据的限制

当前已有一些市场情绪、指数环境是日级别数据，更适合收盘后归因。

未来盘中决策时，必须改成：

- 盘中实时快照；
- 或者只用前一交易日已经知道的数据。

## 3. 算力、网络、存储评估

### 3.1 当前候选规模

从现有数据看：

- Pool1+Pool2 合并候选中位数约 `14` 只/天。
- 近期最大观测约 `30` 只/天。

这个规模非常轻。

### 3.2 本机实测

本机 DuckDB 上，抽取最近 30 只候选，计算某一分钟的相对放量历史基准：

- 总耗时：`0.2576s`
- 单只股票约：`8.6ms`

所以当前规模下，本机完全够用。

### 3.3 如果未来扩展到 300 只

粗略估算：

- 每分钟写入 `300` 行。
- 每天约 `300 * 241 = 72,300` 行。
- 一年约 `1700万` 行。

DuckDB 可以承受。

CPU 不是主要瓶颈，真正要防的是：

- Tushare API 延迟；
- 网络抖动；
- 权限或 token 异常；
- 重试逻辑拖垮下一分钟；
- 写库锁和 dashboard 读库冲突。

### 3.4 工程约束

盘中服务需要记录这些指标：

- 每次 API 请求耗时；
- 返回行数；
- 缺失股票数；
- 特征计算耗时；
- 写库耗时；
- 通知发送次数；
- 连续失败次数。

如果某一分钟失败，应该跳过本轮并告警，而不是阻塞下一分钟。

## 4. 阶段一：集合竞价回补与特征

### 4.1 数据表

已新增 `auction_bar` 表，字段：

- `ts_code`
- `trade_date`
- `auction_type`
- `price`
- `vol`
- `amount`
- `turnover_rate`
- `volume_ratio`
- `source`
- `created_at`

主键：

- `(ts_code, trade_date, auction_type, source)`

其中 `auction_type` 先支持：

- `open_realtime`：`stk_auction`
- 后续可扩展 `open_after_close`：`stk_auction_o`
- 后续可扩展 `close_after_close`：`stk_auction_c`

### 4.2 回补范围

已完成回补：

- `2025-01-01` 至 `2026-06-26` 本地交易日历；
- 每个交易日调用一次 `stk_auction(trade_date=YYYYMMDD)`；
- 每次约 `5000-6000` 行；
- 实际写入 `1,901,255` 行，覆盖 `345` 个交易日；
- `2025-01-02` 至 `2025-01-15` 的 `10` 个交易日返回空，后续归因时不要把这
  10 天当作缺失异常。

### 4.3 特征方向

先做这些集合竞价特征：

- 竞价成交额；
- 竞价成交额相对过去 N 日中位数；
- 竞价量比；
- 竞价换手率；
- 竞价价格相对昨收涨幅；
- 竞价价格距离涨停价；
- 竞价成交额在当日 pool 内排名；
- 竞价成交额在全市场百分位。

### 4.4 验证方式

回补后不立刻改交易策略，先做归因对比：

- 有集合竞价特征 vs 没有集合竞价特征；
- top1/top3/top5 排序收益差异；
- 是否能过滤高开低走；
- 是否能提前识别高概率上板。

## 5. 阶段二：A股分钟RT接入

等 `A股分钟RT` 开通后做。

### 5.1 接入接口

- `rt_min`：盘中批量取多只股票最新分钟。
- `rt_min_daily`：必要时补齐当日开盘以来单只股票分钟。

### 5.2 写入表

继续写 `minute_bar`，但 source 区分：

- 历史分钟：`tushare`
- 实时分钟：`tushare_rt`

### 5.3 盘中循环

每分钟流程：

1. 读取今日 pool1+pool2 监控列表。
2. 拉取实时分钟。
3. 写入 `minute_bar`。
4. 更新每只股票的盘中状态。
5. 计算强承接、突破、放量、临近涨停等信号。
6. 触发模拟盘买入或提醒。
7. 写入诊断事件。

## 6. 阶段三：流式特征引擎

核心原则：历史 replay 和未来 live 用同一套状态机。

每只股票盘中维护：

- 截至当前分钟最低价；
- 截至当前分钟最高价；
- 累计成交量；
- 累计成交额；
- VWAP；
- 最近 5/10 分钟成交额；
- 是否突破 T 日高点；
- 是否收复关键筹码位；
- 是否接近涨停价。

开盘前预先准备：

- T 日高点；
- T 日收盘价；
- 涨停价；
- 90 日价量分布；
- 历史同分钟成交额中位数；
- 历史截至同分钟累计成交额中位数；
- 集合竞价历史分位数。

## 7. 阶段四：模拟盘和告警

模拟盘不做实盘下单，只做验证。

规则：

- B 点信号触发后，按下一分钟开盘模拟买入；
- A 股 T+1，买入当天不能卖；
- 止损、止盈、移动止盈全部可配置；
- 每笔模拟仓记录当时所有特征快照；
- 收盘后复盘 1/3/5/10 日收益。

通知先只推管理员。

## 8. 阶段五：评估后再买更多权限

至少跑 `2-4` 个交易周，再决定是否买其他权限。

评估指标：

- 平均收益；
- 中位收益；
- 胜率；
- 最大回撤；
- 跳空止损率；
- topN 稳定性；
- 集合竞价特征是否有增益；
- 实时分钟特征是否明显优于旧实时源。

购买决策：

- 如果行业共振明显有效，再买 `申万实时行情`。
- 如果策略扩展到 ETF，再买 ETF 权限。
- 如果行业分钟级回测被证明必要，再买 `申万指数分钟`。
