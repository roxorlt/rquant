# 手动盯盘名单：同事务权威状态

对应 v2 C4.8 和 C12.1 的「盯盘名单」范围。最终路径是个股/选股结果发出受保护命令，PageControl 在自己的 SQLite 事务中更新名单，Serving 把有界名单封入同一数据代，网页从该代查看状态，新告警评估角色按同一已发布范围读取。本片只实现可嵌入 PageControl 事务的名单领域表与操作；不开放页面按钮，也不触碰旧 monitor 的运行名单。

**分级：高风险。** 名单将来决定哪些股票接受报价与告警，写入竞争、命令重放或陈旧删除会造成漏报/误报；这里冻结首片范围，最终候选按此模型一次独立审查。

## 威胁与失败模型

- 资产：每位已认证用户的手动盯盘成员、入列来源、可选价格档位与到期时间，以及版本号。信任边界：浏览器输入不可信；PageControl 注入的用户身份和其单个 `BEGIN IMMEDIATE` 事务可信；Serving/React 尚未接入。
- 失败路径：相同股票的并发新增/删除、旧页面用过期版本覆盖新状态、进程在写入后回执前崩溃、非法代码/金额/时间/超大名单、已过期成员被当作仍在盯盘。测试仅用私有临时 SQLite 文件及假用户；不读 `.env`、真实凭据或生产库。
- 不变量：同一 `(owner_id, ts_code)` 仅一个当前状态；新增/删除必须按预期修订号比较并在事务内原子递增，删除保留墓碑以防 ABA；不匹配明确冲突，不猜测成功。PageControl 后续须在**同一 SQLite 事务**把该状态变化与命令终态一并提交，避免“双写”不确定效果。已过期的成员不进入有效名单；未知过期时刻不按已过期处理。读取必须有界且稳定排序，返回当前修订号供后续 CAS。
- 排除：本片不做 PageControl 命令、Serving 发布、网页 API、React 交互、行情订阅或通知；不声称「加入盯盘」可用。目录/进程权限和正式资源容量留到生产接线验收，不能由合成 SQLite 测试替代。

## 首片验收

1. 建立有类型的输入/输出：`owner_id`、A 股代码、来源（个股详情/选股结果/池子成员）、最多 8 个升序且互异的正有限价格档位、可选 UTC 到期时刻；用户身份由未来服务端注入。仓储接收现有 SQLite 连接，不自建连接或提交事务。
2. 新增仅在头不存在且期望版本为空、或墓碑/过期行版本匹配时生效；活跃成员再次新增必须携带当前版本，才允许更新。删除只能针对未过期活跃成员的匹配版本。所有成功操作修订号严格递增；失败不留部分行。相同入参的命令重放最终由 PageControl 同事务命令回执挡住，仓储本身不能假定它已发生。
3. 显式时刻的有界读取区分活跃、已删除、已过期；返回版本和稳定的 `(ts_code)` 顺序。过期行保留版本和原内容供再次加入，但不算有效成员；墓碑仅保留身份与版本，可精确查询而不进入名单扫描。每位用户最多 500 个未过期的活跃成员；超过容量明确拒绝写入，不截断静默发布。
4. 聚焦红绿测试覆盖新建、更新、删除、墓碑再建、旧版本冲突、两个连接竞争、事务回滚、过期边界、非法输入与容量；Ruff 和 diff 检查通过。后续接命令/Serving/React 前，台账仍记「部分且未发布」。
