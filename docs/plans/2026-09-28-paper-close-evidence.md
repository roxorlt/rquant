# 模拟盘关闭订单的可验证证据

**分级：高风险。** `paper_order` 的最终状态会影响用户对委托和资产的判断；当前取消/过期只有不可还原的事件哈希，合法关闭也会使指令历史及账户来源停止发布。本增量只补新关闭事件的证据和读取验证，不做生产账本迁移或切流。

## 决策与替代方案

1. **选用：复用不可变账本 attestation。** 新关闭操作在同一 SQLite 写事务中，把最终 `PaperOrder`、最后一份执行回执身份和固定契约版本组成可重算的摘要，作为新的 `order_close_v2` attestation 事件。历史读取在同一只读事务中用最终订单和回执重算摘要，再核验对应 attestation 行及其时间。这不添加第二套订单权威，也不修改 v5 物理模式。
2. 独立 `paper_order_close_receipt` 表能直接索引决定/持久化时间，但需要 schema、锚与离线迁移；对这次只展示最终状态的页面没有必要。若未来产品要展示两种时间或完整旧史，再单独设计迁移。
3. 把历史移成独立 Serving 来源可以让缺证据时账户继续更新，却不能证明已关闭订单的状态，且增加 authority/可选来源与代际切换。先解决证据缺口；真正的账本完整性错误继续阻断同一权威来源，不用来源拆分掩盖它。

## 冻结的失败模型

- **资产与边界：** v5 `paper_broker` SQLite 的意图、执行回执、成交、最终订单与不可变 attestation 是受信证据；`recent_order_history()` 是 Serving 前的有界读取边界。网页不读主库，浏览器不提交关闭事件。
- **失败路径：** 直接 SQL 伪造 `CANCELLED`/`EXPIRED`，改动最终订单的时间、数量或拒因，复用别的订单的关闭事件，关闭后写入先于最后成交，只有旧 `order_close` 哈希的历史记录，缺失/重复/晚于读取截止的 attestation；大量 attestation 导致无界扫描。
- **不变量：** 新关闭前必须将当前订单与最后不可变执行回执核对，并维持现有时间顺序；同一写事务更新订单和追加 `order_close_v2`。事件摘要绑定完整最终订单及前一执行回执身份，但不把未持久化的决定时刻伪装成可重建字段。读端只接受事件种类、摘要、不可变链和可见时间都匹配的唯一关闭事件；旧事件无证据时保持拒绝。任何矛盾不返回“没有记录”，不吞异常继续发布。查询须有明确的行数/步骤上限，容量不足时拒绝，不静默跳过。
- **明确排除：** 旧关闭事件的猜测性回填、账本 v6 迁移、前端新增关闭按钮、完整历史分页、生产数据库写入与运行时配置切换。

## 实施与验收

1. 先在 `tests/unit/test_paper_order_history.py` 与 broker 关闭测试写红测：正常接受单取消、部分成交后过期可读；SQL 伪造关闭、跨订单事件、缺事件、改时间/拒因、旧事件和未来事件仍拒绝。写路径如发现当前订单与最后回执不符，也必须拒绝关闭且不写新 attestation。
2. 在 `paper_broker.py` 增加纯函数生成版本化关闭摘要；`close_open_order()` 在现有事务更新后取最终订单并追加 `order_close_v2`。读取窗口收集至多 200 条已关闭订单的摘要，单次有界查找相应 attestation，验证唯一性、内部摘要、截止时间和同一账本 head。未关闭订单继续按最后执行回执完整核验。
3. 直接回归 `runtime_builder_paper`：有新证据的合法关闭后仍可发布账户及指令窗口，重复心跳不改写来源代；无证据或伪造状态保持失败。Serving/Web/API/React 契约不变，仅状态从不可用变成真实「已取消」「已失效」。旧关闭订单仍明确是 M10 未覆盖范围。
4. 跑 broker/history/source/Web 聚焦测试、Ruff、差异检查，以及受影响的前端状态测试；最终候选安排一次独立审查，限定上述失败模型并集中报告。更新进度台账，不把本地候选当作正式发布。涉及生产数据或 runtime authority 的动作继续按项目单独授权规则处理。

## 本地候选验收

已在集成分支实现并经一次独立终审，无冻结范围内 P0/P1/P2 阻断。实现者的 broker/history/source 聚焦测试 99 项、Serving/Web 22 项和容量回归 1 项通过；审查者复跑 Python 51+1 项、前端状态 17 项，Ruff 与差异检查通过。新合法取消及部分成交后过期可读，关闭后账户来源继续发布；伪造、跨订单、重复、旧式与截止时间不符的事件仍拒绝。事件指纹无索引，读端以 100 万 SQLite VM 步为容量上限，超限明确失败。旧 `order_close` 记录不升级，正式数据代、生产验证和 Streamlit 替代均未完成。
