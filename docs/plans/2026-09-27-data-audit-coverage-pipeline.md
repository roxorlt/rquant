# 日线覆盖率审计接线

对应 v2 C1.2。目标是让数据中心展示有来源的月度覆盖率、缺口与质量问题，并能区分「未审计」「审计失败」「审计完成」。本地实施不运行生产审计、不更改生产定时器或数据库。

**任务分级：普通任务。** 本片只从调用方已固定的一代只读数据库取证并生成研究报告，不写生产数据或改变共享调度。后续接入生产写入、定时器或回补执行时重新定级并单独授权。

## 方案与边界

考虑过三种入口：网页请求时扫描 `daily_bar`，Serving 每次遇到新副本即重扫，或研究任务在收盘后扫描一次并发布小产物。前两者会把约 10 GB 副本的扫描负担放在交互/发布热路径上，也无法把未完成的采集日与真正缺口分开。采用第三种：研究面负责一次性取证与计算，Serving 只读有界、可核验的审计产物，API 和 React 只呈现同一数据代。

职责依次为：固定副本与截止日的任务入口 → 单连接 SQL 证据读取器 → 现有 `data_audit_coverage` / `data_audit_quality` 纯函数 → 带来源与状态的研究产物 → Serving 小表 → 类型化 API → 数据中心页面。每层只解释自己能证明的事实；缺交易日历、无权威涨跌停或停牌事实时显示「暂无可靠结果」，不得算作健康或零异常。

## 第一片：同连接日线覆盖证据

1. 新增 `src/rquant/data_audit_evidence.py`。入口只接受调用方已经固定的只读 DuckDB 连接、非空的副本代标识、审计起点和经调用方确认采集完成的 SSE 交易日。用同一连接读取该区间逐日 `trade_calendar` 和 `daily_bar` 行数，不在此模块打开数据库或选取“今天”。限定日期跨度和结果行数；重复日历、缺自然日、非 SSE 日历或区间外数据报错。
2. 把证据交给现有 `DailyBarCoverageRequest` 与 `audit_daily_bar_coverage`。月度比例以交易日为分母；首尾缺口、跨月缺口和休市日误入数据均保留。结果绑定调用方的副本代标识和完成交易日。行数为零的开市日是缺口；缺失的日历是无法审计。
3. `tests/unit/test_data_audit_evidence.py` 用独立小 DuckDB 文件构造完整日历、跨月缺口、休市日脏行和边界缺日，核对真实 SQL 到纯函数的端到端结果。另测重复行、超预算和不允许的连接写入。只跑本片及覆盖率纯函数测试、Ruff、diff 检查；最终候选一次独立审查。

本片不改 `data-audit` CLI、不生成页面可读的成功状态、不增加生产扫描。其结果只是下一片任务产物的输入，不能作为已经上线的 C1.2。

## 后续片及验收

1. 研究任务 `data_audit` 在采集完成后固定只读副本代与明确截止交易日，调用覆盖证据读取器；质量规则只在同代可核验的涨跌停、停牌和字段空值事实齐备时运行。失败、未评估与发现异常分别写入报告，不用空问题列表代替成功。
2. 报告带审计 ID、数据代、截止日、规则版本、月度覆盖与缺口、质量问题和未评估原因，作为有界不可变研究产物发布。Serving 核对摘要与上限后投影到可选小表；旧数据代缺表时旧页仍可读，但覆盖结果显示未发布。网页 API 从一次借用的数据代读取，React 以短中文、图表和问题列表呈现，帮助信息放提示中。
3. 合成全链验证从同副本真实 SQL → 研究产物 → Serving → API → 桌面/390px 页面；明确测未审计、最近失败但有旧成功、跨代切换、缺口与异常。正式约 10 GB 副本的耗时与资源预算、生产任务及页面切流分别实测和授权，不能用小样本通过代替。

回补计划/执行属于 C1.3，既不由审计任务自动触发，也不因发现缺口而修改主库。
