# 池子入池价的不可变运行凭据

**目标**：把“这只股票的入池日收盘价属于这次选股结果”变成可复核事实，再向原型的成员表和日 K 提供入池价、可比较的涨幅。

**分级：高风险。** 新切片改变生产选股回执、DuckDB 迁移和共享 Serving 合同。只先在隔离工作树实现与验证；生产建表、迁移、配置、部署和页面切流仍按项目规则单独授权。

## 失败模型与不变量

资产是已发布的成员期、入池价、结果版本与用户看到的涨幅。信任边界依次是日终输入、主库事务、只读副本、Serving 数据代、Web API 和页面。现有 v1 回执只绑定成员集合；事后同时改写 `screen_result.close` 与 `daily_bar.close`，会让两表仍然相等，却把新价格错误归到旧结果版本。单独比较两张当前表不能跨越这个边界。

必须保持：新价格凭据与成员行在同一事务生成；同成员重跑但价格改变时，价格凭据与结果身份改变；旧回执、缺价、价格/因子口径不明、摘要不合、跨数据代与副本换代只给未知，不从当前价倒推。真实零命中仍是成功运行。成员日期与原有画布可独立可读，价格证明失败不撤掉整页。排除实盘成交价、分红现金流入账和跨源推测；入池价文案固定为“入池日收盘价”。

## 方案选择

可选独立价格事件账本、发布后封存整个选股结果文件，或给现有原子运行回执增加价格摘要。选择第三种：它与已有成员摘要处在同一事务，Serving 可在同一副本复核，无需让网页读取主库。旧 v1 回执保持可解读但不证明价格；新 v2 回执绑定按代码排序的 `ts_code + close` 规范表示，空值也有确定表示，非有限价不能变成可显示价格。新 `result_version` 包含回执版本和价格摘要。

## 分片验收

1. 扩展 `ScreenRunReceipt` 的版本化模型、原子写入、DDL/迁移和研究同步。用手工构造的结果验证价格变化而成员不变时版本变化、零命中、同日重跑、事务失败回滚、旧 v1 读取及同步降级。生产迁移只记录待执行步骤，不在本地开发阶段执行线上操作。
2. Serving 从同一稳定副本重算新摘要，并核对入池日 `screen_result.close` 与 `daily_bar.close`。匹配才发布 `entry_close`；v1、改写单表或双表、缺价、缺日历或窗口截断都保留入池日期但价格未知。用真实发布器和网页 API 的合成链验证跨代不串价。
3. 网页成员表显示“入池日”和“入池日收盘价”；有证据时在同数据代日 K 标记入池日与价格线。入池后涨幅另用同副本的最新可比较收盘价与权威复权因子计算，并标明口径；缺因子、停牌或当前日仅有盘中价时显示“暂无可靠涨幅”，不能把原始历史价直接与盘中报价相除。桌面、390px、键盘、空态与换代路径验证。

每片只做一次最终候选独立审查；发现问题按冻结失败模型定向修复。正式约 10 GB 副本负载与生产资源限制须在切流前实测，不能由小型合成库通过推断。
