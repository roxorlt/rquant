# C6 日线组合回测：共用执行账本的首片

接续 CC `frontend-plan-v2.md` §4.6 与本项目 [绩效指标库](2026-09-27-performance-metrics-slice.md)。本片先在隔离研究目录中，以已冻结的逐日输入生成可逐日对账的组合结果；随后再接 Lab 任务、产物索引、基准与回测页。页面不得从旧 `strategy_trade.ret_pct` 推算组合净值。

**分级：普通任务。** 首片新增离线研究运行器与有类型结果，不修改现有模拟盘账本、生产数据或发布契约。主要风险是前视数据、成交口径和净值账本不一致；若后续开始修改模拟盘执行契约或生产数据，须重新按高风险任务冻结边界。

## 第一性原理与职责

- 一次回测是给定输入、配置和代码版本的**确定性账本重放**，结果首先是现金、订单、成交、持仓和估值的逐日核对，图表只是这些事实的视图。不可为了画出曲线而从单笔交易收益倒推资产净值。
- `src/rquant/backtest/` 只负责：按日历和调仓规则确定目标、将目标与已有持仓转换为订单意图、按时间顺序驱动执行、封存逐日快照。仓位上限复用 `portfolio.weights.allocate_target_weights`，回撤控制后续复用 `portfolio.drawdown`，不在回测模块复制公式。
- 撮合、T+1 可卖量、A 股整手、现金、FIFO 持仓、费用和滑点使用现有 `PaperBrokerStore`、`PaperOrderIntent`、`BrokerExecutionContext` 与 v3 `calculate_execution_costs`。每次回测只在全新、受限的研究任务目录创建自己的账本；绝不传入线上模拟账户路径，绝不直接写线上账户。日线与模拟盘因此从第一笔回测起使用同一执行账本；后续 C6.3 把旧分钟回放切入它并做逐笔差异验收，不再造第二套撮合。
- 行情/池子/排名提供者仅交付有类型、不可变、含来源与可见时刻的交易日快照；运行器不查询 Web 或 Serving，不读主库。Web 只读取同代封存产物，`run` 命令以后走 Lab 准入。仓位规划与数据适配不互相持有服务对象。

## 时序与数据边界

1. 每个交易日均有明确 SSE 日历。日线信号和排名只能使用**前一交易日收盘后、且在当日 09:25 决策截止前已经观察到**的数据；当日开盘价只在成交时使用，当日收盘价只在日终估值时使用。当日盘后数据不得倒灌到当日上午；缺前序日、来源身份、观察时刻或完整日历时该日不可运行。
2. 输入包含：每日候选及排名、股票分类凭据、开盘/收盘价格、停牌与方向性涨跌停封单证据、可用时间、交易日历、成本版本、初始现金、仓位规则及调仓周期。每日/每周/每月/每 N 日按**交易日**定义；配置、输入身份、成本版本和代码版本一并封存。同一代码与输入重复运行，订单、成交、日快照和内容哈希必须一致。
3. 09:26 后竞价可见只对带有明确竞价观察时刻的输入生效；首片只有日线开盘执行，不借日线最高/最低价推断竞价委托或是否封单。缺停牌/涨跌停权威证据的标的不按“可成交”处理，并单独记录“交易条件未核验”；已知停牌、涨停不买或跌停不卖才交给 broker 的封闭拒单原因。不能把数据缺失误称为停牌或封板。
4. 每个调仓日先按已持有量和目标量形成卖单，再按代码稳定排序形成买单；卖单成交后才能把释放的现金用于买单。数量一律向下取到 100 股，不以不足一手为已成交。每笔都经过 broker 的限价、现金、可卖量和 v3 成本判断；买入股的可卖日由完整 SSE 日历给出下一交易日。成交受阻的目标差额保留为实际偏离，不暗中重配其他股票。
5. 每日收盘从同一 broker 账本及当日核验收盘价生成现金、持仓、市值、费用、已实现与未实现盈亏、总资产、日收益与相对初始资金的净值。持仓缺有效收盘价时**当天净值不可用并使本次结果不完整**，不可沿用上日价格或填零；无持仓时现金净值仍有效。执行时刻、入账时刻和日终估值时刻须显式区分。

## 产物与验收

- 首片定义带 `schema_version` 的 Pydantic 请求、逐日行情输入、订单/成交/持仓/净值结果；外部层不传裸 `dict`。每个交易日的 `cash + Σ(quantity × 收盘价) == nav`，现金变动与成交额及费用逐笔对上，持仓股数与买卖成交对上。结果保留原始 broker 订单/成交身份和拒单原因；封闭中文文案留给 API/React 适配器。
- 固定 3 只股票、10 个交易日的手算基准覆盖换仓、被拒单、卖出释放现金、费用、T+1 和空仓；另聚焦覆盖各调仓周期、停牌、方向性涨跌停、缺条件证据、缺收盘价、日历缺行、前视输入、重复运行一致性。对同一日同一意图与报价，离线回测和直接模拟 broker 的订单、成交、费用、现金与可卖量应逐条一致。
- 本片完成只代表**本地离线执行候选**。C6.1 的 Lab `portfolio_backtest`、不可变产物和 Serving 索引，C6.2 基准的封存产物接线，C6.3 旧分钟回放迁移，以及 C7.2 图表/标签页都仍是后续明确验收项；未形成封存产物前，React 不显示可运行或可下载的假按钮。

## 历史来源接线前提

现有 `daily_bar` 没有逐行历史首次可见时刻，`auction_bar`、`minute_bar` 的导入时间也不能直接证明多年前的盘中可见性。下一片适配器不能把事后导入时刻伪造为当日 09:25 的实际观察。真实逐时归档与历史回溯假设须分开建模：前者保留真实接收证据；后者把「前一交易日收盘数据在次日决策前可用」作为明确的模拟假设，并冻结行情版本、日历和分类来源。回溯假设下的结果要在产物和页面标明，缺停牌或涨跌停开盘条件仍不猜测为可成交。接通真实数据前，不把本地合成回测称为可用的历史回测。

下一片先从只读副本的**同一快照**收集交易日历、前日排名/价格、当日开盘与收盘、上市分类、停复牌覆盖和开盘成交条件，再封存有来源摘要的输入；回放只消费封存输入，不在运行中回查不断变化的库。`screen_run_receipt` 的完成时刻与价格摘要可证明某些历史排名当时已形成；`daily_bar` 的 OHLC 只能证明事后的价格事实，不能因此给它补造盘前采集时刻。逐项标出「当时捕获」或「历史回溯假设」，两种来源不能在同一字段里混写。对回溯模式，开盘可成交仍须有完整的停牌覆盖、限价规则与开盘成交证据；只凭日线 open/high/low 或缺行不能判成可成交。适配器应针对每个不可用条件给出封闭原因，避免产生看似完整、实际全靠补值的净值曲线。

## C6.2 本地指数基准候选：数据与证据边界

现有日线采集已在 `ingest.py` 从 Tushare 拉取六只主要指数，并写入 `index_daily_bar`；本片直接读取该表，不新建采集路径。`load_benchmark_series` 默认选沪深 300（`000300.SH`），也可选同一既有六指数目录中的其他代码。调用方提供冻结 DuckDB 文件、`SSECalendar` 和 `BacktestResult`；读取只用一个只读连接、一个事务和一次按代码及日期范围查询，不连接正在写入的主库。

首个回测交易日之前的**上一 SSE 交易日 close** 定义基准净值 1.0；每日日收益为当日 close / 前一 SSE 交易日 close − 1，归一净值为当日 close / 基准 close。来源摘要包含 `source_mode=retrospective_daily_bar`、表名、指数代码、日历来源身份、前日日期与收盘价，以及对实际查询行计算的 `source_identity`；序列还绑定回测结果 `content_hash`。必须逐日覆盖回测结果中连续的 SSE 交易日，缺前日基准、缺任一日、重复日、意外日期、非正或非有限 close 均拒绝；不补值、不以 `pre_close` 猜值。

比较层要求回测账本结果完整、日期完全一致，使用其由账户净值产生的 `daily_return`，调用已有 `performance_summary` 和 `relative_metrics`。它不从 `strategy_trade` 的单笔收益推导组合净值。`index_daily_bar` 的 close 是事后日线事实；摘要不包含或暗示历史当时的采集时刻。该序列只能用于本地离线回顾比较，**绝不可作为 09:25 盘前决策输入**。本片尚未接 Lab 任务、封存产物索引或页面。
