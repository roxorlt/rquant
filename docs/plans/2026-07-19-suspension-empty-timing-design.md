# 空停牌时段语义修复设计

## 背景

成长板策略在 `2026-04-30` 的资格输入面板只有 `1982 / 2007 = 98.754%` 完整，
低于正式研究要求的 99%。逐股核验发现，前一交易日没有日线和指标的 14 只股票都存在
覆盖状态为 `complete` 的 Tushare `suspend_d` 停牌 `S` 事件，但
`suspend_timing` 为空。现有归一化将这类事件标为 `unknown`，导致系统继续要求一份
停牌期间本来就不存在的日线。

Tushare 官方每日停复牌接口样例把全天停牌的 `suspend_timing` 返回为 `None`，而日内
部分停牌返回明确区间，例如 `09:30-10:00`；官方日线接口同时说明停牌期间不提供行情。
生产样本中“空时段 S”与“当日无日线”也完全一致；截至 `2026-07-17` 的只读核验中，
1,133 条空时段停牌 `S` 都没有同日日线，75 条同日分钟记录全部是成交量和成交额为零的
占位行，另有 2 组同股同日停牌与复牌事件必须保持冲突状态。

## 方案

在停牌事实归一化入口统一采用：

- `suspend_type == "S"` 且时段为空：`full_day`；
- `S` 且命中全天文本：`full_day`；
- `S` 且包含明确时间范围：`partial`；
- `R` 或无法解释的非空文本：`unknown`。

在所有分钟缺失豁免、成长板资格和质量审计入口共享同一会话证据分类：

- `full_day`：coverage 完整、至少一条全天停牌、没有复牌/部分/未知事件、没有同日日线，
  也没有非零分钟成交；
- `conflict`：存在全天停牌事实，但同时存在复牌/部分/未知事件、同日日线或非零分钟成交；
- `unknown`：只有部分停牌、复牌或其他不足以证明全天停牌的事实。

零成交分钟占位行不代表发生交易，可以保留；任何同日日线行都与全天停牌冲突。共享查询
必须在检查分钟证据前按 source、股票和日期范围下推，避免规划器或 runner 反复扫描全量
分钟表。

不修改 99% 完整性门，不人工补 K 线，也不原地篡改旧 manifest。部署后对目标历史区间
执行 `suspension-backfill --full-refresh`。截止日不能写死为旧策略资格上限，而是每次从
权威 SSE 交易日历动态取得最近已收盘交易日。命令先在无 DuckDB 写连接时取完所有源快照，
再用一个外层事务重建整段事件、coverage 和 snapshot hash；任何日期失败都会同时回滚
`stock_suspend_event` 与 `stock_suspend_coverage`。

生产刷新前必须生成并验收新备份，停止会写主库的服务和相关 timers。刷新后重新生成同一
代码提交下的 `n_shape`、`growth_board_surge`、`auction_gap` 三个 manifest、dataset
snapshot、binding 和正式回放；`v0.25.1` 的正式门不得复用旧提交生成的制品。

## 验收与回滚

单元测试同时覆盖空时段停牌和空时段复牌。停牌、成长板资格和清单模块测试及全量测试必须
通过。生产重算后，目标区间内每个 SSE 开市日都必须存在完整 coverage，空时段停牌不得
残留 `session_scope != full_day`，`2026-04-30` 输入覆盖应达到至少 99%，新 manifest 的
eligibility hash 必须与旧 manifest 不同。若任何门失败，事务内失败自动回滚；事务提交后
才发现问题则停止后续分钟回补，并从本次操作前的精确数据库快照恢复。代码按精确前一 tag
回滚，历史 manifest 无需删除。
