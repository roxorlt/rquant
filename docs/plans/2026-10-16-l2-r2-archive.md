# L2 R2 日终归档实施计划

## 目标与范围

为已提交的 L2 市场批次增加日终归档、上传验证和按日期恢复。复用当前缓存与 R2 传输客户端。首版保留本地数据，不增加实时数据路径的操作。

风险等级为高风险：变更涉及云存储凭据、历史数据完整性和自动调度。可审计的详细 SPEC、威胁模型和准入结论由本会话的独立证据文件冻结。

## 实施顺序

1. 独立审查 SPEC。冻结缓存、对象、索引、恢复、初始化和部署边界。
2. 实现确定性、有界的原始批次导出。固定本轮末批序号。测试部分提交、损坏、重试和源重置。
3. 实现严格的 R2 验证与恢复。只在全部对象验证后提交索引。远端索引是唯一进度记录。
4. 实现独立归档 service、timer 和专用部署入口。默认工作日上海时间17:20运行。盘中补触发应延期。
5. 使用合成市场批次，在实际 Linux 无开发依赖环境验证 R2 上传、下载、恢复和幂等重跑。不得用合成结果代替实盘容量证据。
6. 对最终候选进行一次独立集中审查。由原实现者定向修复。最多三轮。
7. 在实际云端验证 unit 和日历语法。运行精确提交的仓库 CI，提交独立归档 PR。
8. 周一先让20股全部60路持续通过并正式常驻，再按正式发布门禁安装归档组件。归档部署不重启采集器或 API。

## 验收

实际证据须覆盖多日期恢复、大小与 SHA256、完整原始模型与序号、缺口状态、固定末批边界、失败不发布、丢失本地回执后的远端进度恢复、无变化重跑零上传，以及所有测试进程退出。

部署测试须覆盖来源和制品门禁、已安装核心20股证明、外来 unit 拒绝、首次初始化、升级缺索引拒绝及仅归档回退。

## 不做

不增加上游请求，不处理下单，不删除本地或 R2 数据，不改 bucket 生命周期，不触碰生产数据库，不增加特征计算或通用数据平台。
