# 集合竞价历史缺口受控修复设计

## 背景

Stage 1 三策略验收发现，研究湖中的集合竞价数据存在七个历史交易日缺口：

- 2026-04-20
- 2026-07-07
- 2026-07-08
- 2026-07-09
- 2026-07-10
- 2026-07-13
- 2026-07-14

现有 `research-ingest --recover` 适合从最新权威日期开始，按交易日连续追加分钟和竞价
分区。它会同时发布一分钟线与集合竞价，并要求观察链连续，因此不能用来修复已经位于
权威链中间的单数据集历史缺口。

旧 `auction-backfill` 直接写生产 DuckDB，不维护研究湖的内容寻址版本、catalog、只读
catalog、权威观察和崩溃恢复日志，也会在单日失败后继续处理其他日期。它不满足本次
“七天全部成功才发布”的治理要求。

## 目标

新增一个专用的受控修复命令：

```bash
rquant research-repair-auction \
  --date 2026-04-20 \
  --date 2026-07-07 \
  --date 2026-07-08 \
  --date 2026-07-09 \
  --date 2026-07-10 \
  --date 2026-07-13 \
  --date 2026-07-14

rquant research-repair-auction \
  --date 2026-04-20 \
  --date 2026-07-07 \
  --date 2026-07-08 \
  --date 2026-07-09 \
  --date 2026-07-10 \
  --date 2026-07-13 \
  --date 2026-07-14 \
  --apply \
  --plan-id <第一步输出的 plan_id>
```

第一步会真实请求 Tushare、严格校验每一天并生成内容绑定的计划，但不改本地文件。
第二步重新获取并重建同一计划；只有计划 ID 仍完全一致时，才原子发布全部日期。

## 非目标

- 不修改生产 DuckDB 中的 `auction_bar`。
- 不新增实时交易、下单或 Tick/Level2 能力。
- 不绕过工作日 09:15-15:10 的生产保护窗口。
- 不删除旧 Parquet 内容寻址版本，不改写已发布的历史文件。
- 不把一分钟线与本次集合竞价修复重新绑定发布。

## 数据质量口径

每个目标日期都必须先通过生产只读副本中的交易日与日线全市场完整性检查。

定义：

- `E`：该交易日 `daily_bar` 的去重股票代码集合。
- `O`：Tushare 返回的结构合法、主键唯一、属于目标日期的
  `source='tushare'`、`auction_type='open_realtime'` 行对应代码集合。
- `T`：`O` 中 `price`、`vol`、`amount` 均为有限正数的实际竞价成交代码集合。
- `N`：`O` 中精确满足 `price=NULL, vol=0, amount=0` 的明确无竞价成交代码集合。
- `V = T ∪ N`：结构有效的观测代码集合。
- `M = O - V`：字段只填了一半、包含非正成交值或无穷值的畸形代码集合。

每一天必须同时满足：

```text
|E ∩ V| / |E| >= 98%
|E ∩ O| / |O| >= 98%
|M| = 0
```

Tushare 对没有开盘集合竞价撮合成交的股票会返回 `N` 类行；这是一条明确的零事件观测，
不是接口漏数。它可以证明该代码已被接口覆盖，但没有可交易的竞价价格，因此永远不会进入
集合竞价策略候选。实现使用整数交叉相乘，避免浮点边界误差。以下情况直接令整个批次失败：

- 目标日期非权威 SSE 交易日或日线全市场不完整。
- 接口返回空数据、错误日期、缺字段或重复物理主键。
- 返回行不是 Tushare 开盘集合竞价口径。
- 存在任何 `M` 类畸形行。
- 有效覆盖率或观测精确率低于 98%。
- catalog、只读 catalog、当前权威标记或目标 manifest 在计划后发生变化。

分钟线合成的 fallback 行可以保留在最终分区中，但永远不能计入 Tushare 98% 质量门。

## 合并规则

每个目标日期分别读取当前研究湖竞价分区，并执行以下合并：

1. 保留非 Tushare 来源行，包括分钟 fallback。
2. 使用本次接口返回替换同日期的 Tushare `open_realtime` 行。
3. 业务值没有变化的既有行保留原始 `created_at`。
4. 新增或业务值变化的接口行使用本次真实修复时间作为 `created_at`，不得回填成
   09:26 或其他虚构时刻。
5. 最终分区按物理主键唯一并稳定排序。

## 计划绑定

`plan_id` 是规范 JSON 的 SHA256，至少绑定：

- 动作和 schema 版本。
- 排序去重后的目标日期。
- 干净的 40 位代码提交 SHA。
- 当前权威标记、主 catalog、只读 catalog 的 SHA256。
- 每日预期日线代码数量与代码集合哈希。
- 每日旧竞价 manifest 哈希。
- 每日 Tushare 原始业务内容哈希。
- 每日合并后内容哈希、行数、成交/明确无成交/畸形计数、覆盖率计数和是否变化。

因此数据源返回发生变化、代码变化或任一发布基线变化时，旧计划都不能被 apply。

## 原子发布

整个批次共用 `research-publish.lock`。apply 在锁内完成：

1. 恢复任何既有未完成研究发布事务。
2. 校验权威链、catalog、只读 catalog 和目标 manifests。
3. 再次请求全部日期并重新生成计划。
4. 比对用户提供的 `plan_id`。
5. 在事务目录中复制 catalog，构建全部目标日期的新 immutable Parquet 和 manifests。
6. 构建新的只读 catalog。
7. 写入包含所有目标文件前后哈希的发布日志。
8. 以 CAS 方式发布版本文件、manifests、主 catalog、只读 catalog、修复观察和当前权威标记。
9. 全部成功后删除日志和事务目录。

任何异常都按日志恢复全部旧 manifests、catalog、只读 catalog 与当前权威标记，并删除
本次新建且此前不存在的 immutable 版本文件和修复观察。恢复前先完整预检所有 CAS，
防止只恢复一半。

## 权威链处理

历史分区变化后，旧的日增量观察仍作为不可变证据保留，但它们绑定的分区版本不再是
当前 catalog head。修复发布一个新的 `ResearchAuctionRepairObservation`：

- 指向修复前当前权威观察的内容哈希。
- 记录每个日期的新旧 manifest 与内容哈希。
- 记录 catalog 和只读 catalog 的前后哈希。
- 保持权威最新交易日期不倒退。
- 将 `stable_trading_days` 重置为 0。
- `eligible_for_promotion=false`。

之后第一个正常日增量候选从稳定第 1 天重新开始，连续 10 个交易日后才能再次具备提升
资格。旧内容寻址版本和正式快照仍可按其原始 manifest 解析。

当前权威标记改为可判别联合模型：既接受日增量观察，也接受历史竞价修复观察。权威检查
沿 `previous_observation_sha256` 遍历两种观察，并对当前修复观察校验当前 catalog/lake。

## 运维与可观测性

命令输出 Pydantic JSON，包含：

- `status`: `planned`、`candidate` 或 `unchanged`
- `plan_id`
- 目标日期与每日期质量统计
- 新旧 catalog/manifest 哈希
- 是否重置稳定观察
- observation ID

正式 apply 要求：

- `RESEARCH_CLOUD_INGEST_ENABLED=true`
- 干净的完整提交 SHA
- 非保护窗口
- 主副 catalog 和权威链在执行前完整

本功能不新增 systemd unit。首次七日修复由受控部署流程手工执行，成功后继续使用现有
`rquant-research-ingest.timer` 做日增量。

## 发布版本

受控修复能力首次发布于 `v0.23.0`；明确无成交质量语义修正在 `v0.23.1` 发布。合并前
更新 `CHANGELOG.md` 和相关研究数据文档；合并和 CI 全绿后创建指向合并提交的 annotated
tag，再通过精确 tag 部署。
