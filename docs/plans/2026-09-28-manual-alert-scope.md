# 手动盯盘名单进入告警范围：第一片

对应新前端计划 C4.8 / C12.1。手动名单只给未来显式配置的告警规则提供作用范围；加入名单本身不产生通知，也不推断旧 Pool 1/2 攻击规则的字段。现有云端 `rquant monitor` 启动时只读一次 Pool 1/2，不能把手动名单直接拼进这个旧列表。第一片先给告警评估端提供独立于 Web 的只读范围证据，之后才接行情、规则、投递和页面状态。

**分级：高风险。** 范围错读可能给其他用户发通知、漏报或重复推送。本片只实现可验证的范围读取，不启用告警。

## 冻结的威胁与失败模型

- **资产与信任边界**：PageControl SQLite 是手动名单写入权威；Serving 发布经核验的不可变同代名单与状态；告警范围读取器只消费这一数据代，并保留 owner、股票、版本和到期信息。浏览器、旧 monitor、报价源和通知通道均不能提供名单权威。
- **失败路径**：名单尚未激活、成对投影缺失或损坏、发布代换代、同一股票属于多个 owner、删除墓碑、到期恰在评估时刻、旧数据代残留、超容量或来源时间倒退。上述异常不能复用上一次手动范围，也不能影响旧 Pool 1/2 的独立运行。
- **必须保持**：一次读取只用一个核验 Serving 数据代和一个明确评估时刻；不跨代拼接。有效成员按 `(owner_id, ts_code, version)` 保留，删除和到期立即排除；可信零成员与来源不可用分开。缺/坏证据使手动范围不可用，调用方不得把它当空范围或继续按旧范围发告警。未来规则求值必须额外要求启用规则、当日新鲜报价与显式触发条件；名单本身从不触发。
- **排除项**：本片不修改 `rquant monitor`、告警规则库、通知 outbox、systemd/nginx/sudoers、生产配置、手动名单写入或前端；不会访问 `.env`、凭据或生产数据。旧 monitor 对 Pool 1/2 的投递保持原状。正式接线和停用旧 monitor 要先取得回放对照及单独生产授权。

## 本片验收

1. 非 Web 模块能从一份借用中的 Serving 数据代取得有类型的 `ready` / `unavailable` 范围和代际身份；最多读取现有名单合同允许的有界行数。
2. 合成数据代验证新增、删除、到期、同股双 owner、空名单、未激活、缺表/状态不一致、换代和坏行。来源不可用时不给可用于规则求值的成员集。
3. Web 私有 GET 继续按认证用户过滤；共享的来源核验逻辑只有一份，告警端不导入 Web route 或认证对象。PageControl / Serving / Web 现有聚焦行为不退化。
